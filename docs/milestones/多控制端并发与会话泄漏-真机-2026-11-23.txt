二、台架 1：六个控制端并发（scripts/verify-multi-client-e2e.sh，新增）
  结构：同一台真机被控端上同时起 **3 个视频端 + 3 个端口映射端**，三个映射端各自
  `--forward 127.0.0.1:<自己的端口>:127.0.0.1:<同一个 echo 目标>` —— 也就是
  「跨会话多条端口映射同时打同一目标」，各打一条 1 MiB 全双工流（内容各不相同）。
  为什么必须分成两类客户端：`--forward` 在 main.rs 里会 `drop(c.video)`、独占整条会话，
  同一条会话拿不到画面。这条限制本身也在报告里写清（它不是缺陷，是设计）。

  真机两轮：**42 通过 / 0 失败 / 0 跳过 × 两轮**，数字：
    · 被控端日志 6 条「会话已授权，开始推流」，6 条都协商出 `window=Some(16)`
    · 三个视频端各 **195 帧 / 解码丢帧 0 / 首帧 511~534 ms**（单会话基线 220~230 ms，
      多出来的部分是 3 个 x264 同时起编码器的启动争用，不是回归）
    · 三个视频端存帧与真机自己 x11grab 截图：**相关系数 0.9999 / MAE 0.45%**（三份相同）
    · 三条 1 MiB 全双工流：**42~59 ms**，逐流 sha256 一致；每个映射端统计
      「连接 1 / 上行 1048576 / 下行 1048576」—— 同一个目标上三个会话互不串、字节不混
    · 被控端**同一个 PID 全程没变**，日志无 panic/ABRT/invalid pointer
      （这条是 2026-10-26 那次并发会话 SIGABRT 的回归判据，Xlib 没有内部锁）

三、台架 2：会话反复开关的泄漏回归（scripts/verify-session-churn-e2e.sh，新增）
  每条会话都会在被控端起一个 ffmpeg 编码子进程、开一次 Xlib、注册一个 bulk 流；
  这类东西「开一次没事、开二十次开始漏」最难在单次验收里发现。台架串行 12 条
  （`--headless --seconds 3 --fps 5`）+ 并发 4 轮 × 3 条，每收一条 / 一轮就采一次样：
  VmRSS / Threads / `/proc/<pid>/fd` / 子进程数 / ffmpeg 子进程数。静置 8 秒再采终值。

  真机两轮：**14 通过 / 0 失败 / 0 跳过 × 两轮**
    第一轮：基线 rss 5700 KB / threads 17 / fds 10 / children 0
           终值 rss 25744 KB / threads 17 / fds 10 / children 0 / ffmpeg 0
           增量：RSS +20044 KB、线程 0、句柄 0；预热后每条会话平均 +730 KB
    第二轮：基线 5708 KB → 终值 15420 KB（+9712 KB），预热后每条会话平均 +193 KB
    两轮的 ffmpeg 子进程、子进程数两次都**归零**；线程峰值 19~21、收尾回到 17；
    句柄数全程 10 一条没变；被控端 PID 全程没换；日志无 panic/ABRT；24 条「会话结束」都记到。

  结论口径：RSS 从 5.7 MB 涨到 15~26 MB 是**分配器缓存/碎片**（两轮斜率差 3.8 倍、
  第二轮在并发段里还回落过），不是单调泄漏 —— 判据写成「预热后每条会话平均多占 ≤2 MB」，
  两轮分别是 730 KB / 193 KB，都过。**这条别改回「终值必须等于基线」**：那样每次都会红。

四、台架 3：高延迟链路下的按流窗口（scripts/verify-bulk-window-wan-e2e.sh +
  scripts/latency-proxy.py + scripts/calibrate-latency-proxy.py，都是新增）
  做法：控制端 ↔ 中继这一腿插一个用户态延迟代理（协议字节盲转发，加密仍在两端），
  档位 0 / 25 / 50 / 100 ms 单向；每档在同一会话里跑 1 MiB 与 4 MiB 两条全双工流。
  真机：**11 通过 / 0 失败 / 0 跳过**，每一档两条流 sha256 都一致、统计上行=下行=5 MiB。

  实测（uulan，经代理）与判据器标定（**裸代理、不含 uulan**）：
    单向延迟   uulan 1 MiB / 4 MiB      裸代理 1 MiB / 4 MiB
      0 ms       44 / 116 ms              22 / 30 ms
     25 ms       91 / 321 ms              80 / 90 ms
     50 ms      377 / 838 ms             144 / 177 ms
    100 ms      558 / 1731 ms            232 / 278 ms

  读法：内网（0 ms 档）uulan 只比裸代理多 1~4 倍毫秒级开销，**按流窗口在内网不是问题**；
  RTT 变大以后多出来的那部分就是「窗口 16 帧换一次信用」的代价 ≈ 每 MiB 一个信用 RTT，
  吞吐封顶 ≈ 窗口/RTT（1 MiB / 200 ms RTT ≈ 5.2 MB/s，实测 4 MiB 档 2.4 MB/s）。
  **口径**：延迟只加在控制端↔中继这一腿，真实广域网两端都慢 —— 这里的 RTT 是**下界**、
  吞吐是**上界**。要把广域网吞吐做成产品能力，得把窗口帧数变成握手协商值（新增字段 +
  两端取 min），不是改常数就行。

六、这一轮新学到的口径与坑
  1. **`--forward` 与视频互斥**：`main.rs` 里 `if !args.forward.is_empty() { drop(c.video); … }`，
     同一条会话里既看画面又做端口映射是做不到的。台架要「并发视频 + 并发映射」就得多起进程。
  2. **put/get 的远端路径不要带 `:` 前缀**：`--put f :/tmp/x` 会被拼成 `/home/mis/:/tmp/x`
     并报「上级目录不存在」；`:/` 是 `--ls` 的「此电脑」写法。绝对值直接写 `/tmp/x` 就行。
  3. **延迟代理不能「读一块、sleep、写一块」**：那样等于按 16 KiB/延迟 限速，量出来的是带宽
     不是 RTT。正确形状是「读 → 入队（带到期时间）→ 定时写出」，多个块同时在途。
  4. **判据器必须先标定**：裸代理在同一档位只要 144 ms（50 ms 档）而 uulan 要 377 ms ——
     没有这一步，「377 ms」会被误读成产品在这条链路上的下限。`scripts/calibrate-latency-proxy.py`
     就是干这个的，改代理实现后要重跑它。
  5. 采样脚本里 `ps --ppid` 数子进程比 `pgrep -f ffmpeg` 可靠：后者会把别的会话/别的台架的
     ffmpeg 数进来（本机就同时跑着编码器）。

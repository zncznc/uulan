静态审查询出的「最该担心」的点（因此值得跑）：`C2H`/`H2C` 都 `#[derive(Debug)]`，而被控端

把哨兵原文落进日志。实测没有发生。

哨兵四个，两个方向都走真链路：
  A = 20,000 字符（:0 上由探针 SET → 控制端读 → 线上 → 被控端写 :99）
  B = 20,000 字符（:99 上 SET → 被控端读 → 线上 → 控制端写 :0）
  超限 = 200,000 字节（必须被 ClipSync 拒发，只许留字节数）
  小对照 = 21 字节（同会话对照组，证明「拒发」不是链路死了）

「确实同步过」的互证（不是空跑）：
  控制端   剪贴板同步 : 发送 2 / 接收 1（本机写入失败 0 / 本机读取失败 0）
  被控端   剪贴板同步统计 sent=1 recv=2 errors=0 skipped_oversize=0 skipped_empty=0 skipped_same=61
  外部探针读回：:99 `GET-BEFORE len=20000`（收到 A）；:0 `GET-BEFORE len=20000`（收到 B）
  第二轮     控制端 发送 1 / 被控端 recv=1 skipped_same=22（小对照走通）
  超限路径   DEBUG uulan_clip: 剪贴板内容超过上限，不同步 bytes=200000 cap=196608
             （同一次持有被轮询到 3 次，全部只留数字，一个字内容都没落盘）

「哨兵没进日志」（本轮的主张）：

诚实边界：
  - 判据探针 `x11_clip_probe` 与被控端生产后端是**同一份 X11 代码**（进程与 X 连接独立），
    独立性弱于第三方 xclip；因此第二轮改由**独立 python 所有者**挂哨兵，并用 21 字节
    小对照同时钉「链路活着」与「拒发不是死路径」。
  - 超限哨兵只能走「文件 → python 持有者」这条路：argv 传 300KB 会被内核拒
    （`/usr/bin/env: 参数列表过长`，第一轮那步 rc=126 就是这个，与产品无关）。
  - 哨兵文件、测试台、真机与本机两侧口令临时文件**全部已删**；`:0`/`:99` 不残留哨兵
    （X11 剪贴板随持有者进程退出失效，符合设计）。测试台 down、中继 21996 已停。

四、M6 日志脱敏的代码改动（新增 Shape 层）+ 新二进制的真机复跑
--------------------------------------------------------------
金丝雀跑完后回头审「还有哪条路径能把原文写进日志」，静态查出**两处兜底日志把整条消息用
Debug 打出来**，而这两个枚举里正躺着原文与凭据：

| 位置 | 原来 | 消息里躺着的秘密 |
|---|---|---|
| 控制端 `watch.rs` 视频通道兜底 | `debug!(?other, "视频通道上的其他控制消息，忽略")` | `H2C::Clip{text}` 剪贴板原文、`H2C::TermOut{data}` 终端原文 |
| 被控端 `main.rs` 中继推送兜底 | `debug!(?other, "中继推送")` | `ToEndpoint::ClientReady{session}` **会话票据原值** |

`RUST_LOG=debug/trace` 一开就是原文落 journal，而这两条恰恰是「对面发了我没预料的东西」
那条路径 —— 排障时最可能打开日志的场合。修法不是删日志（排障必须知道是哪一类消息），
而是新增 `crates/uulan-protocol/src/shape.rs`：`Shape::shape()` 对每个变体返回 `'static`
类名，实现是 exhaustive match，以后新增消息忘了考虑脱敏就编译不过。两处调用点改成
`shape = other.shape()`。提交 **a9e55f4**。

三条新单测：`debug_derivation_really_does_leak_payloads`（把「Debug 确实带原文」钉住，
记录为什么必须有这一层）、`shape_carries_only_the_variant_name`（剪贴板/终端/票据/设备 ID
四类哨兵都不在 shape 里）、`shape_names_are_greppable_identifiers`。

本机：**cargo test --workspace = 457 通过 / 0 失败 / 1 忽略 / 0 警告**（基线 454 + 这 3 条）；
cargo build --release 零警告；协议一个字节没动，两端不需要同批升级。

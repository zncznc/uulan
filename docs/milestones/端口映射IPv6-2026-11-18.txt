端口映射 IPv6（2026-11-18）—— 真机验收 9 条断言全过

`--forward` 第一版遇到 `[` 直接报「不支持 IPv6 字面量」，理由是**不想猜分隔符**。
那个理由是站得住的（`::1:2222:22` 里到底哪个冒号是分隔符，猜错就是把人送进错误的
地址），但结论可以不这么保守：用**方括号**把地址括起来，歧义就消失了 —— 这也是
URL / curl / ssh 的通行写法。

## 改了什么（crates/uulan-client/src/forward.rs）

- 解析器换成 `split_top_level`：按 `:` 切分，但 `[...]` 整体是一个段（里面可以有冒号）。
- 方括号里**只接受 IPv6 字面量**：`[db.internal]` 是笔误，直接报错，不让它悄悄当主机名用。
- 半边方括号 / 空段（多余冒号）都给出明确错误，**一律不猜**。
- 绑定地址与目标主机都支持 IPv6：`[fe80::1]:2222:[::1]:22`。

单测 7 条全过（新增 3 条：IPv6 目标、IPv6 绑定+目标、方括号规则的四个反例）。

## 过程中两件必须记住的事

### 1) 这台 Windows 开发机的 `::1` 能 bind 不能 connect

第一次在 Windows 上跑，A/B 两案都红，报 `os error 10013`（「以一种访问权限不允许的
方式做了一个访问套接字的尝试」）。最小实验证明**跟 uulan 无关**：

    listener on [::1]:59136
    connect 失败: [WinError 10013]
    网卡列表里 singbox_tun（metric 5）比 Loopback 还优先

也就是说本机 IPv6 环回被 TUN 的默认路由接走了。处理方式不是绕过它，而是**让脚本先探
这个前置**：探不到就退出 2 并写「不要据此判定 IPv6 端口映射有问题」。真数据是在麒麟上
取的 —— 那台的 `::1` 正常（`disable_ipv6=0`）。

这条与 10-31 那次剪贴板、11-12 那次编码是同一类：**先分清「被测的东西坏了」和「测量
环境坏了」**。区别只在于这次是路由，不是权限和代码页。

### 2) 我自己在这轮里删过一次真机上的源码

上传包时我把 Windows 反斜杠路径（`C:\Users\...\Temp\x.tgz`）交给了 `tar`，它没写出文件；
而我那条命令里紧跟着 `rm -rf crates scripts docs`，于是真机上那份构建副本的源码被删了、
包却不存在。二进制还在（生产在 `/opt/uulan` 和 `~/.local/uulan/bin`，不受影响），
源码用正确的 POSIX 路径重新打包上传、36 秒重编就恢复了。

教训：**破坏性动作不能和「产物的产生」写在同一行**，中间必须先验证产物存在。
（顺带记一条环境事实：给 MSYS 的 `tar` 用 Windows 反斜杠路径等于没写文件。）

## 仍未验

- 端口映射的 **IPv6 白名单「放宽」方向**（`portmap_allow` 写 `fd00::/8` 后确实能连到
  别的 IPv6 机器）：需要第二台带全局 IPv6 的目标机，这台麒麟只有链路本地地址
  （`fe80::…`，带 scope 的连接不可靠），造不出这个场景。
  **但安全相关的那一半已经验了**（见下节）：白名单确实约束 IPv6 目标，新语法不是后门。
（**中继走 IPv6 这条已于同日验掉**，见下一节；上面只剩「白名单放宽到 IPv6 网段」未验。）

## 追加：中继自己也走 IPv6（同日验证）

`--bind` / `--server` 都是字符串直传，理论上 `[::1]:port` 能解析；但「能解析」和
「三个进程真的在 IPv6 上跑出画面」是两件事。`scripts/verify-relay-ipv6-e2e.sh` 在麒麟上：

    ⓿ 本机 IPv6 回环可连                        PASS
    ① 中继在 [::1]:21990 听上（--bind 认 IPv6）  PASS
    ② 被控端注册成功，设备 ID 906975190（--server 认 IPv6） PASS
    ③ 控制端连 [::1] 收工 rc=0                  PASS
       真收到画面：AU=3020 解出帧=3019 首帧=105ms PASS
    ④ 中继日志出现 IPv6 对端地址 / 记录被控端上线  PASS

    退出码 0，全过：中继走 IPv6 端到端可用

顺带修掉判据自身一个弱点：我原先用 `解出 *: [0-9]+` 抓数字，而实际标签是「解出帧」，
于是账目里印出 `解出=?` —— **判据印出问号就是判据说不出话**，当场改成 `解出帧? *: …`。

## 追加：白名单对 IPv6 目标同样生效（同日验证）

新语法最怕的是「顺手开了个后门」：如果白名单只按 IPv4 判断，那 `[::1]` 就成了绕过
`portmap_allow` 的通道。`scripts/verify-portmap-allowlist-ipv6.sh` 在麒麟上验：

    ⓿ 本机 IPv6 回环可连 / [::1] echo 与 127.0.0.1 echo 都在听   PASS
    ① 把被控端 portmap_allow 收窄成 ['127.0.0.1/8']（不含 ::1）  PASS
       被控端带着收窄后的白名单上线（设备 ID 895720596）        PASS
    ② 请求 [::1] 目标 → 被控端明确以白名单为由拒绝               PASS
       反面对照：IPv4 回环目标放行且字节原样回显（ECHO …）      PASS
       被控端日志有「端口映射已建立」                          PASS

    全过：白名单对 IPv6 目标同样生效

反面对照这一格我写错过两次，两次都是**判据自己没制造条件**：

1. 第一次把对照目标指向 `127.0.0.1:21988`，而那个 echo 只绑在 `::1` 上 —— IPv4 那边
   压根没人听，于是「IPv4 也被拒」是假象；
2. 第二次补了 IPv4 echo，但**没有真的去连本地监听端口**，被控端就没有理由去连目标，
   日志里自然没有「端口映射已建立」（`连接 0 / 上行 0 字节`）。

教训：**反面对照必须自己制造出「应该成功」的完整条件**，否则它证明不了任何事 ——
一个永远失败的反面对照，和一个永远通过的正面对照一样没用。

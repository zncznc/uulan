鼠标捕获模式两端接线（--capture / F8）· 2026-11-17 05:00 夜批
================================================================

兑现上一班（11-17 01:00）归档里留的话：「将来做鼠标捕获模式，传输层就是
C2H::MouseMoveRel」。本轮把控制端这一半接上：**窗口模式下把本地指针锁进窗口
并隐藏光标，移动改发相对增量原样上线**；被控端一行没动（接收半边自 M2.5 起
就完整 —— 这本来就是「协议先行、单侧缺勤」家族里唯一还挂着的一条）。

一、接线内容与三条纪律（crates/uulan-client/src/capture.rs，纯状态机）
--------------------------------------------------------------------
1. **不掺画幅换算**：DeviceEvent::MouseMotion 的增量直接进 MouseMoveRel。
   一旦按缩放比例去乘，「对面指针动多少 = 本地手动多少」就不成立。
2. **亚像素残余跨事件累积**：0.75 的样本 4 个必须攒出 3 格；IEEE754 的浮点
   结合律欠账（0.6×5 加出 0.9999999999999997）必须在下一个样本兑现 ——
   单测两条各钉一边（精确二进制小数 + 浮点欠账），这不是漂移是记账。
3. **超过被控端单条钳位 ±10000 的原始事件拆条上线，不是夹掉**：
   25000 → 10000+10000+5000；「夹掉」会吞掉用户的真实手移动。
   拆分上限与被控端 mapper 同源（常量注释指到对方文件）。

window.rs 侧的接线决定（都有理由，别改回去）：
- 捕获态**丢弃 CursorMoved**（绝对上报）：抓握时 winit 自己会 SetCursorPos
  制造一条 WM_MOUSEMOVE —— 它必须被守卫丢掉，否则指针在会话开始就跳一次。
- **抓握/解除以系统调用成败为准**：set_cursor_grab 失败就明说「捕获模式不
  启用，继续按绝对坐标」，绝不带病宣称在捕获；解除失败则保持捕获态并警告
  （切回绝对上报会两套移动并存）。
- F8 是本地开关，**不转发**到被控端（否则「退出捕获」顺手在对面按了次 F8）。
- run() 里 listen_device_events(Always)：winit 的 Windows 后端 WhenFocused
  不挂 RIDEV_INPUTSINK（源码写死），无人值守夜批没有前台窗口可言 ——
  必须 Always，否则指针增量一条都进不来。
- 标题标注「捕获模式（F8 退出）」，每秒刷新路径与切换瞬间都走 shown_title。

main.rs 参数闸门（--capture 只准在有 winit 事件循环的地方活）：
+ --headless / --inject / 文件操作 / --term / --terms / --power / --forward /
  --status 一律当场报错；其中 --devices/--forget 是**提前返回分支**，
  闸门必须放在它们 return 之前 —— 这条是 exe 级反例实测抓出来的
  （先只挂了常规闸门时，--capture --devices 直接去连中继了）。
+ --capture 与 --no-input 矛盾（只读模式一条不发，捕获只会把本地光标钉死）。

五、未验项（如实）
------------------
- **F8 真键盘路径未验**：键盘走 WM_KEYDOWN 需要窗口前台焦点，夜批保证不了。
  toggle 状态机与标题由单测钉住；交互式会话里一按便知。
- 触摸板惯性滚动（PixelDelta）在捕获态与相对移动的混用手感：设计上是
  并存（滚轮走 MouseWheel 原路），没有判据可钉，留给交互验收。
- /opt/uulan/bin 正式更新仍要 root（sudoers 未装）—— 继续压着，
  与捕获模式无关。
- 判据是**注入的**相对移动（与硬件同源进 raw input，winit 不按
  LLMHF_INJECTED 过滤 —— 源码核对过）；「真硬件鼠标在真桌面」的差异
  不在本判据范围。

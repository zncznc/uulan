本班没有新功能，干了两件事：把一条脆弱判据改成能说人话的，以及把三条长期挂着的

## 一、判据加固：mic_uplink 那条不再「只说等不到」

全量 42 个测试二进制并发跑时，`crates/uulan-client/tests/mic_path.rs` 的
`mic_uplink_flows_and_stops_by_eof` 报过一次红：

    panicked at mic_path.rs:163: 等不到：上行计数接近 3 秒的量（>120 帧）

单跑一次是 **135 帧 / 33740 字节 / 3.22 秒**，所以 >120 只留 11% 余量，而这条链
**设计上满载会丢帧**（有界队列）。更要命的是失败信息里**没有实测数**，看到红的人
无法判断是掉帧还是节奏慢。

改动（判据强度没降）：把这处 `wait_until` 换成显式轮询，失败时把**实测帧数与字节数**
打出来，并注明单跑基线 135；量级的最终判据仍是下面第 4 步的 24 KB..120 KB 字节区间。

    改完全量：547 通过 / 0 失败（cargo 退出码 0）

同类纪律（2026-11-17 那条终端背压测试已经做过一遍）：**固定 sleep 后的一次性断言
是慢机器/满载下的假红制造机；轮询到条件成立、超时才输，并且失败必须带实测值。**

## 二、三条「未验」的真实阻塞条件

### 1) 捕获模式 F8 真键盘路径 —— 卡在**这台 Windows 开发机会话是锁屏的**

写了 `scripts/verify-capture-f8-e2e.sh` + `scripts/capture-sendkey.py`（SendInput 注键盘、
窗口置前）。脚本能起来、能拿到正确的窗口标题（

    uulan · 麒麟真机(linux) · 1920x1080 · 画面 1280x720 · 30 fps · 9026 kbps · …
    · 延迟 0.4ms · 捕获模式（F8 退出）

），但 `SetForegroundWindow` 一直失败，加了 ALT 技巧、AttachThreadInput、
SwitchToThisWindow 三条兜底仍然不行。直接查输入桌面才看清：

    本进程 window station: WinSta0 / desktop: Default
    当前前台窗口: (2821192, 'Windows 默认锁屏界面')

**本机自己被锁屏了**——锁屏会话根本不接受前台切换，所以 F8 送不进被测窗口。
这不是 winit/焦点策略的问题（那是我原先的假设），也不需要改代码。

结论：脚本已就绪，**解锁这台 Windows 后一条命令就能验**：

    bash scripts/verify-capture-f8-e2e.sh --device 805747189 --password-file D:/uulan-bin/host.pw

四条判据：① 起手就在捕获态（日志 + 标题带 `· 捕获模式（F8 退出）`）
② 按 F8 后日志「捕获模式已关闭：光标回到本地」且标题后缀消失
③ 再按一次出现第 2 次「已开启」且后缀回来 ④ 全程没有「指针锁定失败」。

顺带记一笔：脚本里读窗口标题又踩了一次 **PowerShell 默认 OEM 代码页把中文吐成乱码**
（和 2026-11-12 剪贴板那次一模一样），标题判据会因此假失败。凡是跨 PowerShell 取
非 ASCII 字符串，必须显式 `[Console]::OutputEncoding=[Text.Encoding]::UTF8`。

### 2) uinput 输入兜底 —— 卡在**这台真机不给普通用户 /dev/uinput**

    /dev/uinput   crw------- root root
    mis 属组      mis adm cdrom sudo dip plugdev users lpadmin sambashare   ← 不在 input 组
    内核模块      uinput 未加载
    可写          否

也就是说：现在写 uinput 后端，**在这台机器上一次都跑不起来**，只会多一条没人执行过的
代码路径 —— 按本项目的规矩（被 SKIP 的分支等于没验）不做。要解锁这一格，二选一：

    a) 加 udev 规则让 input 组可写 /dev/uinput（需要一次 root）；
    b) 让被控端以 root 跑（与「被控端必须以桌面用户身份跑」的设计冲突，不建议）。

XTest 目前是唯一输入后端，且在真机上全绿（打字/拖拽/滚轮/组合键都验过），所以这条
不是功能缺口，是**鲁棒性储备**。

### 3) 播放延迟 / 信宿被争用 —— 卡在**缺少两端都有真实声卡的机器**

量播放延迟要有「一端出声、另一端收声」的物理回路。现有条件：

- 麒麟：有 USB 音频（`alsa_output….analog-stereo-spdif-output.monitor` 采集、
  `alsa_input….analog-stereo-spdif-input` 录音），但输出是 **spdif 数字口**，不接线
  回不到输入，做不了声学回环；
- 这台 Windows：`ffmpeg -f dshow -list_devices` 的音频输入**枚举为空**（没有输入设备），
  播放也没有可用波形设备，所以既不能当出声端也不能当收音端。

要验这两条，需要：两台都有模拟声卡（或有线把 spdif 出接进输入）的机器，或者给这台
Windows 插一个 USB 声卡/耳麦。**给这台 Windows 插一个 USB 耳麦即可同时解锁**：播放延迟
（本机放、本机录回环）和「信宿被别的程序争用」（同一 sink 两个播放者）。

## 三、这轮的方法教训

以前写「未验」就完事了，读者（包括后来的我自己）无法判断是**没人做**、**没条件做**、
还是**做不了**。这轮把三条都追到了**具体的系统事实**（锁屏的前台窗口、`/dev/uinput`
权限位、dshow 枚举为空），于是每条都能写清「解锁它需要什么」——这比一个「未验」有用得多。

## 一、挑命令是实测挑出来的，不是想当然

| 路 | 真机实测 | 结论 |
|---|---|---|
| `paplay --format=s16le --channels=2 --rate=48000 <raw 文件>` | 「打开声音文件失败」rc=1 | **不通**：这台麒麟（PulseAudio 13.99）的 paplay 只吃 libsndfile 认得的文件 |
| `cat raw \| paplay --format=... -` | 「open()：没有那个文件或目录」rc=1 | **不通**：这个版本根本没有 raw/stdin 这条路 |
| `cat raw \| aplay -q -t raw -f S16_LE -c 2 -r 48000 -` | rc=0，且信宿 monitor 录得到 | **采用**（ALSA default 经 `/usr/share/alsa/pulse-alsa.conf` 落到 pulse 的默认信宿） |
| `pw-play` | 这台机器没有（`which pw-play` 空） | 没验过的东西**不写进候选表**，免得它去抢播放顺序 |
| 另起 null sink + `PULSE_SINK=uulan_verify aplay ...` | monitor 录回 451700 字节**全是零**（峰值 0） | **别打这个主意**：ALSA→pulse 插件按默认信宿落，`PULSE_SINK` 对它不起作用；要做「不出声的验收台」得先 `set-default-sink`，而那是改机器状态的事 |

候选表 `player_candidates()` 与 PATH 查找 `find_in_path_with(name, dirs, is_exe)` 都是纯函数，
所以**两个平台的单测都能钉住它们**（Windows 上看不到 cfg(not(windows)) 的任何代码，这条是
本仓库唯一能给这段逻辑本机证据的路）。新增 2 条：

- `player_args_are_exactly_the_decoders_format` —— `-t raw` / `-f S16_LE` / `-c 2` / `-r 48000` /
  末位必须是 `-`（stdin），且这两个数字必须来自 `CHANNELS` / `SAMPLE_RATE` 本身。参数与解码器
  输出一字不差是这条链路的立身之本：差一个字符的现场表现是「ALSA 当场退出」或
  「一声不响但统计在涨」，后者最难查。
- `find_in_path_follows_path_order_and_executability` —— 按 PATH 顺序、只认真正能执行的那项
  （同名不可执行文件不算），找不到时是老实的 `None`（不赌第一个目录）。

## 三、真机验收：`scripts/verify-audio-playback-e2e.sh`（在麒麟上跑）12/0/0，跑两轮

测试台与被控端都用独立配置与独立中继（127.0.0.1:21998，台账在 /tmp 的工作目录里），
设备 ID 是测试台自己生成的（302986016 / 322663151），**不碰正式服务的身份与口令**。
被控端 `--audio-source lavfi:sine=frequency=440:sample_rate=48000`、
`--capture lavfi:testsrc2=size=640x480:rate=15`、`--once`。

第一轮（真机 22:45:51–22:46:01，同会话）：

- 控制端退出码 **0**；`已请求被控端发送音频 sink=Speaker`
- **`实时播放已接上 program=aplay rate=48000 channels=2`** ← 本机真的起了播放进程的证据
- `被控端正在推流 codec=opus/ogg 64k 48000Hz 2ch detail=lavfi:sine=frequency=440:sample_rate=48000`
- 音频统计：收到 **494 帧 / 113744 字节** → 解出 **9.9 秒** PCM（峰值 2945）→
  **播放 1892640 字节**，错误 **0**
- **`实时播放已收尾 program=aplay`** ← 播放进程自己退出，没走到 1500 ms 宽限 kill，尾巴没被切
- 独立判据：`parecord` 从 `alsa_output.usb-Generic_USB_Audio-00...monitor` 录回
  **1926140 字节 / 10.03 秒 / 峰值 2841 / 5 个 2 秒窗 / 440Hz:1000Hz = 27 倍**
- 对照组（**没人播时**录 3 秒）：44 字节 / 0.00 秒 / 峰值 0 —— Pulse 把挂起的信宿一个样本都不写。
  这条是判据不自证的凭据：录到的那段 440 Hz 只可能来自本轮这条链路。
- 同会话画面：解出 2560 帧 / 丢帧 0 / 首帧 122 ms（合成源不限速，帧数只作活性证据）
- 第二轮 22:47：同样 12/0/0，**440Hz:1000Hz = 33 倍**、解出 9.9 秒 / 播放 1892640 字节 /
  错误 0、画面 2516 帧 / 丢帧 0 / 首帧 144 ms

为什么判据必须是「录回来」而不是「播放字节数」：`played_bytes` 只证明字节写进了子进程的
stdin，而管道能一声不响地吞掉一整晚。数字要落在 PulseAudio 上才算数。

顺带补的一个观测口：`play_loop` 里播放写入失败以前只加计数就 `break`，原因（含子进程退出码）
不落日志——现在 `warn!` 出来。这与剪贴板那条教训同族：「统计里少了 N 个」必须能说清是谁拒的。

## 八、仍未验（别写成已验）

- **音量/流被别的程序争用时的行为**：本轮没测 Pulse 被别人独占或 sink 忙时的表现
  （代码路径是「起不来就 warn + 只解码不播放」，但没有真机反例）。
- **播放延迟**没量过（只验了「有声音且是那条正弦」）。
- 多信宿机器上「播到哪块」只做了默认信宿的保守选择（`pactl info` 里认名字），没有第二块声卡可测。
- 开发机（Windows）这一侧的实时播放本轮只复跑了 `--audio-save` 那条 WAV 路，
  `waveOut` 那半条没重测（未改，且 M7 首验时已在真机听过来）。
- 麦克风（控制端 → 被控端）方向仍未做，这是 M7 剩下的唯一一格。

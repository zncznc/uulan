二、参数怎么定的（scripts/probe-sink-tail-latency.sh，在真机上跑）
-----------------------------------------------------------------
台架：静音保活流把信宿钉在 RUNNING → 起录 monitor → sleep 1 → 起一条
`ffmpeg -re … sine=440 | aplay <参数> -` → 起声位置 − 起流时刻 = 末端段。
起流时刻与录音在同一台机器上，不需要对表。

  aplay 参数                monitor 台架的末端段
  ─────────────────────────────────────────────
  不给（现行生产）                    1.098 s
  -B 100000 -F 25000                  0.598 s
  -B  50000 -F 12500                  0.498 s   ← 与下一档已无差别
  -B  20000 -F  5000                  0.498 s
  -F  10000（不给 -B）                1.198 s   ← 起作用的是 -B 不是 -F

三、第二个口径：PulseAudio 自己的账（不信录音台架）
-----------------------------------------------------------------
monitor 台架的时间基要经过 parecord 的首块落盘，绝对值不可全信，所以同一条流
再问一次 Pulse：`pactl list sink-inputs` 里这条 aplay 流的
「缓冲延迟 + 信宿延迟」（采样时 LC_ALL=C 钉成英文，判据不跟现场语言走）。

  aplay 参数                     Pulse 自报末端段
  ─────────────────────────────────────────────
  不给（现行生产）        300208 + 136571 = 0.437 s
  -B 100000 -F 25000       61958 +  30934 = 0.093 s
  -B  50000 -F 12500       23333 +  22979 = 0.046 s
  -B  20000 -F  5000       19583 +  14440 = 0.034 s

内核侧对照（播放中读 /proc/asound/card1/pcm2p/sub0/status）：
  delay: 900 帧 = 18.75 ms（硬件 FIFO）；appl_ptr − hw_ptr = 598 样本 = 12.5 ms
  （正好一个周期）—— 于是「PCM 进 aplay → 变成声音」三段的账对得上。

**默认取 -B 50000 -F 12500**。理由：两个独立口径都在 50 ms 这一档饱和
（再往下只有 12 ms 可测收益），而播放缓冲薄到 20 ms 以下时，进程被调度打断一次，
现场就是一声「咔哒」。

现场开关：`UULAN_AUDIO_TAIL_MS=<5..1000 的整数毫秒>`（只影响 unix 侧 aplay；
周期取缓冲的四分之一）。**值写坏 = 起流失败并把开关名写进错误里**，
绝不静默退回默认（与 power_allow / mic_sink 同一条纪律：「拼错的词被当成没配」
的静默降级在现场最难查）；空值按没配处理。三条单测钉住：
默认档就是实测档 / 参数不随机器状态变 / 开关严格性与空值语义。

四、判据器本轮抓到的三个自身问题（先审判据器，再审产品）
-----------------------------------------------------------------
① 「过半」起声判据会落在**启动爬坡**里，绝对值随爬坡形状抽签。
   同一个旧二进制，本轮首跑用旧判据量出「上行 0.44 s」，而 11-18 两轮是 1.19 s
   —— 0.75 s 的差全在判据里。把 loop.wav 的逐窗功率打出来才看清形状：
   会话起来后约 2.2 s 内，440 与 880 **两路一起**「爬到稳态的 63% → 掉回 0 →
   再爬进稳态」，「过半」阈值正好落在这段爬坡里。
   → 判据改成「达到稳态 90%」（onset90）。
② 「连续 9 窗都过 90%」这一版又被**拍频纹波**抽签：同一新二进制两轮起声
   1.550 / 2.000 s（0.45 s 抖动）。双向同会话时 440 与 880 互相拍频，逐窗功率
   上下窜，硬与门的落点随机。
   → 最终判据 = **0.45 s 段的滑动中位数达到稳态 90%**。改完两轮：
   起声 1.450/1.600 与 1.350/1.600 s，抖动回到 ±0.15 s 的口径内。
③ monitor 台架的绝对值不能再当「总延迟」：它说 0.44~0.59 s，Pulse 自己说这条流
   只缓冲 0.064 s。差的那一截在「PCM 进 aplay 之前」（解码器起来到首块 PCM：
   现网一轮 TailWatch 报「首包解码=44ms 首包播完=71ms」，测试台一轮 146 ms）。
   排除法（scripts/probe-onset-ramp.sh，四条台架，全程挂静音保活流钉住信宿）：
     paplay（Pulse 原生客户端）放 1.5 s 音 —— 无爬坡
     aplay 读文件                          —— 无爬坡
     aplay 读 stdin（ffmpeg -re 喂）       —— 只有 0.45 s 的窗边沿，不掉回去
     aplay 读 stdin + -B 50000             —— 无爬坡
   → 信宿、Pulse、ALSA→pulse 插件都不是那个「爬坡-掉零-再爬」的来源；
     而换上 50 ms 档之后，真链路里那段 2.2 s 的爬坡**基本消失**
     （起声位置 2.45 → 1.45~1.60 s）—— 说明它原本就是「大缓冲先吐一口、
     生产者再追上来」的起流形状，不是网络、也不是这台机器的固有性质。

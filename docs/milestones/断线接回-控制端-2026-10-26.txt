uulan · 控制端的断线接回（会话中途）· 2026-10-26 夜间批

────────────────────────────────────────────────────────────────
一、为什么做这个

被控端在 2026-10-25 已经能自己重连中继了（进程不退、设备 ID 不变）。但现场最常
碰到的断线恰恰是「升级 = 重装 + 重启服务」，那一刻**控制端**这边的会话也断了，
而客户端把「画面流结束」当正常收尾：实测 8.8 秒后退出、退出码 0，窗口跟着关掉。
于是用户体感是「你们升级一次，我这边窗口就没了」。

这次补的就是这半边：控制端断开之后自己接回去，窗口不重建。

────────────────────────────────────────────────────────────────
二、难点与做法（细节见 docs/DESIGN.md 的对应小节）

难点不在「再连一次」，而在 winit 的事件循环**只能建一次**（而且必须占主线程）。
所以必须把「窗口」和「一条会话」拆开：

- session::Live —— 会话槽。帧通道 / 统计 / 输入口 / 被控端状态四样东西跨会话不变，
  一条会话起来时成组替换。窗口只读它，完全不知道「重连」这回事。
- VideoWatcher::start_into —— 帧通道由调用方持有。**这是本节最容易踩的坑**：
  每次都新建通道的话，窗口手里那个接收端会指向一条再也没人写的通道，
  表现是「画面永久冻住，而统计一切正常」（AU 在进、解码器在出）。
- VideoWatcher::wait_end() —— 用一条「会话还活着」的通道判结束。
  不能用 next_frame() 返回 None：窗口模式下帧通道的发送端由会话槽持有，永远不会全掉。
- session::drive —— 会话循环：连 → 跑 → 断了按 1/2/4/8/15 秒退避重连，
  连续失败 8 次（--reconnect）放弃；「这条会话真的出过画面且撑过 2 秒」才清零计数。
- 值得重试的错误和连接阶段**有意不同**：会话中途的「设备不在线（Offline）」是预期
  （中继刚重启、被控端还在退避里没重新注册），必须继续等；口令错 / 被锁 / 忙 /
  协议不匹配一律不重试（那是往对面失败计数里加数）。
- 断线瞬间摘掉输入口、保留屏幕上最后一帧（残影比黑屏更像「正在恢复」），
  标题写「已断线，正在接回（第 N 次 · 原因）」。注意 redraw 在「这一帧画过了」会提前
  返回，那一处的标题刷新也要照做，否则这句话永远不会出现。
- 重连放弃时退出码 4（不是 0），脚本才不会把「画面冻着」当成功。
- 剪贴板后端改成每条会话新建（X11 后端是常驻线程当 selection 所有者）。

三、本机全链路（scripts/verify-reconnect-e2e.sh，新增）

真 server + 真被控端 + 真控制端，第 8 秒把中继打死、1 秒后重新拉起：

headless（25 s）：
  会话 1 解出 1947 帧 / 丢帧 0 / 首帧 52 ms
  第 1 次重连撞上「Offline 被控端不在线」→ 2 秒后第 2 次成功，接回耗时约 4 s
  会话 2 解出 3379 帧 / 丢帧 0 / 首帧 57 ms
  接回后存下的 PPM：2 764 800 字节像素，非零 202 914（不是全黑，说明真在出画面）
  收尾「会话       : 建立 2 条 / 断线接回 1 次」，退出码 0

窗口模式（25 s，同样中途打死中继）：
  窗口没有重建，painted=2238，收尾「会话：建立 2 条 / 断线接回 1 次」，退出码 0

另外三个既有 e2e 未受影响：文件传输 6 MiB sha256 往返一致、端口映射 256 KiB 单流 +
两条并发逐字节一致、终端真 PTY 退出码原样回来。

四、真机实测（麒麟 V10 SP1，192.168.223.15，海光 C86，X11 1920x1080 @ 30 fps）

部署：从 HEAD（0ff58f6）打包 → 真机换源码（保留 target/）→ 真机编
`cargo build --release -p uulan-server -p uulan-host -p uulan-client`（35.7 s，零警告）
→ `install.sh --userland --no-start` 装进前缀（client sha 与 target/release 一致；
server/host 二进制与上一版逐字节相同，所以不需要重启它们）。

中继由 `systemctl --user kill -s KILL uulan-server` 打死，systemd 自动拉起。

1) 基线（改前的同版本对照，12 s headless）
   354 帧 / 29.5 fps / 首帧 241 ms / 丢帧 0 / 码率 10.1 Mbps
   与真机 x11grab 截图逐像素：**相关系数 0.9984 / MAE 0.71%**
   （历史基线 29.1 fps / 0.9982 / 0.71% —— 没有回归）

2) 中途断线（75 s headless，第 18 s KILL 中继）
   会话 1：18.1 s、543 帧、30 fps、丢帧 0、首帧 227 ms
   中继：01:43:59 被 KILL（status=9/KILL）→ 01:44:01 重新 Started，
        NRestarts 8→9、MainPID 变成 1891520（进程确实是新起的）
   被控端：MainPID 1833732 / NRestarts 12 **一次都没变**（上一轮的接回逻辑）
   控制端：第 1 次重连撞 Offline（被控端还没重新注册）→ 2 秒后成功
        01:44:04 会话 2 建立 ⇒ **从被杀到画面回来 4.3 秒**
   会话 2：52.5 s、1575 帧、30 fps、丢帧 0、首帧 221 ms
   退出码 0；收尾「会话       : 建立 2 条 / 断线接回 1 次」
   接回后的帧与**接回之后**再抓的真机截图比对：**相关系数 0.9970 / MAE 0.73%**
   ⇒ 接回的是那台机器当时的真实桌面，不是冻住的那一帧

3) 窗口模式（45 s，第 12 s KILL 中继）
   窗口**没有重建**（日志里 `窗口已就绪` 只出现一次），
   断开 → 1 s 退避 → Offline 失败 → 2 s 退避 → 接回，共约 4.6 秒；
   painted=1326、退出码 0、收尾「会话：建立 2 条 / 断线接回 1 次」。
   断线期间位图不动（同一帧不重复 present），所以 painted 的增长是真证据。

五、仍未验 / 已知边界

- **是「重连一条新会话」，不是「续传旧会话」**：屏幕会停 3–5 秒（退避 + 被控端重新注册），
  回来的是新编码器/新解码器，剪贴板重新读基线。
- 文件传输 / 端口映射 / 终端不跨断线：它们本来就是独立的一次性会话（`--ls` / `--forward` /
  `--term` 各自一个进程），断了就退出，这一版没改。
- 重连「放弃」那条路径（连续 8 次失败 → 退出码 4）只在单测与本机 e2e 里验过
  （`Reconnect` 纯逻辑 + 窗口 about_to_wait 的 Finished 分支），真机没跑过 ——
  那要求中继长时间不回来，无人值守时不好造也容易把机器留在坏状态。
- 中继「半开连接」超时踢人仍未做（上一轮就记着），所以极端网络下服务端可能仍认为
  设备在线；被控端/控制端都靠自己的退避重连恢复。

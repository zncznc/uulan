一、扫描（为什么是这两条）
────────────────────────────────────────────────────────────────
两端主循环的 match 表全量点名（控制端 `watch.rs`/`control.rs` 收 H2C，被控端
`session.rs` 收 C2H），结论：**除以下两条外，所有消息都已两端接通**。

  · `C2H::VideoFocus` —— 发送 0、接收 0（连 `other => 忽略` 的显式分支都没有）。
  · `C2H::ClipOffer` / `H2C::ClipOffer` —— 两个方向都只有「如实记一笔」的接收分支，
    两端谁都不发；而协议里**没有定义过任何“拉正文”的消息**，声明了也取不到货。

────────────────────────────────────────────────────────────────
二、裁决 1：video_focus 删除 —— 不是「未接线」，是「机理不存在」
────────────────────────────────────────────────────────────────
它躺在协议里十年没人接的第一原因，是它假设的编码器能力根本不存在。实测留证：

环境：开发机 ffmpeg 9.0-full_build（gyan.dev，configuration 同时含
`--enable-libx264 --enable-libx265`），源 = `lavfi testsrc2 320x240`，
管线参数与被控端一致（ultrafast + zerolatency + crf 35）。

六种空间写法全部被 libx264 拒绝（ffmpeg 非零退出、输出 0 字节）：

    zones=d-15\:0,0,160,120        → invalid zone: "d-15:0,0,160,120"
    zones=d-15\:0,0,160,120\:b0    → invalid zone: "d-15:0,0,160,120:b0"
    zones=d-15\:0,0,10,8           → invalid zone: "d-15:0,0,10,8"（宏块单位猜想）
    zones=d+15\:0,0,160,120        → invalid zone: "d+15:0,0,160,120"
    zones=d+3\:120,80,230,145\:b0  → invalid zone: "d+3:120,80,230,145:b0"
                                      ↑ **x264 文档自己的示例写法**，同样被拒
    zones=0,0,160,120\:d-15        → invalid zone param: 160 = (null)

对照 x264 官方 zones 语义（mewiki / doom9 存档）：
`--zones <start_frame>,<end_frame>,<q=…|b=…>`，多条 zone 以 `/` 分隔 ——
**按帧号的时间区间**，跟屏幕坐标无关。协议注释里那句「AE 风格：控制端只关心
看到的区域」是骨架阶段拍脑袋写的错误假设，两端未接只是它的症状。

处置：变体直接删除，**不做任何兼容**（它从没上线过：两端都不发，wire 零变化，
PROTO_VERSION 保持 4）。反例钉在 `uulan-protocol` 的
`tests::adjudicated_dead_messages_do_not_parse` —— 两个方向的 json 都必须解不出来，
哪天有人把它加回去，测试先变红逼人读这份归档。

「某块区域更清楚」如果要真做，正确路线是独立里程碑项，二选一：
① 双流合成：整帧低码率 + ROI 裁剪高码率，控制端合成（要动视频通道的子流框架）；
② 换 x265（它有真正的空间 zones）—— 代价是编码延迟与麒麟现网 ffmpeg 配置，先评估。
不该做的是留一条没有机制的死消息骗未来的自己。

────────────────────────────────────────────────────────────────
三、裁决 2：clip_offer（两个方向）删除 —— 拉取机制从未定义
────────────────────────────────────────────────────────────────
先按夜批纪律排查过「不删会不会更危险」：担心过一种隐藏炸点 —— 超大剪贴板文本
越过 `MAX_FRAME = 8 MiB` 把会话打死。**排查结论：不存在**。现行机制完整且有测试钉：

  · `uulan-clip::MAX_TEXT_BYTES = 192 KiB`（两端共用 `ClipSync` 纯状态机）；
  · 超限**不发送、不截断**，计入 `skipped_oversize` 并打带原因与数字的 debug 日志
    （已有测试 `oversize_is_counted_not_truncated` 钉住）；
  · 192 KiB 远低于 8 MiB 帧上限，帧层的超长报错在剪贴板这条路不可达。

offer 是「大内容省一次往返」的早期设想，但配套的拉取消息一直没设计 ——
与 video_focus 同病：只有声明、没有机制。删除；`Shape` 名字表、被控端与
控制端的接收分支同步清掉（控制端保留 `Ok(other)` 兜底日志，纪律不变）。

=====================================================

环境
----
- 被控端：mis@mis-pc（银河麒麟 V10 SP1，海光 C86），DISPLAY=:0，X11，ffmpeg 带 libx264
- 被控端版本：HEAD d5d534a（本轮从 HEAD 打包 → 真机编译 → install.sh --userland 重装，
  `systemctl --user kill -s KILL` 拉起，设备 ID 805747189 不变，host.json sha256 不变）
- 控制端：Windows（本机，同一 HEAD），headless 模式
- 屏幕：`xrandr` 报 VGA-0 / HDMI-A-0 都 disconnected，帧缓冲可在 1024x768 ↔ 1280x720 之间改

  且完全可逆 —— 脚本的 trap 里恢复原值。

怎么验的（`scripts/verify-resolution-follow.sh`，19 条断言）
-------------------------------------------------------------
真机 + 真服务（正式 systemd 单元，不是测试台），控制端 headless 跑 30 秒；会话出画面之后
第 11 秒在真机上改帧缓冲，第 17 秒用 `ffmpeg -f x11grab` 抓一张真机截图，收工后：
- 控制端日志里必须出现「被控端分辨率/编码画幅变了，解码器已重建」且 `screen_w/h` 是新值；
- 收工统计的「当前画幅」与 `--save-frame` 存出的 PPM 头必须是新尺寸；
- 会话数必须仍是「建立 1 条 / 断线接回 0 次」（换分辨率不许断线）；
- 存出的帧与真机截图逐像素比对（480x270 盒式降采样后算相关系数）≥ 0.99；
- 被控端 journal 里必须有对应的「分辨率已变」重启记录；
- 结束时分辨率必须已恢复。

实测（最终一轮，19 通过 / 0 失败）
----------------------------------
会话 A：1024x768 → 1280x720（会话中途拉大）
- 连接横幅报 `屏幕 1024x768`（开局就对）
- 第 11 秒改 fb；控制端 `解码器已重建 screen_w=1280 screen_h=720 from_w=1024 from_h=768`
- 收工：解出 887 帧 / 丢帧 0 / 首帧 201 ms / 28.8 fps（被控端自报 30.00 fps）/ 4786 kbps
- 当前画幅 1280x720；存帧 1280x720；会话「建立 1 条 / 断线接回 0 次」
- 与真机 1280x720 截图：**相关系数 0.9999，平均绝对误差 0.39%**

会话 B：1280x720 → 1024x768（会话中途缩回）
- 连接横幅报 `屏幕 1280x720`（**这条是修过的 bug，见下**）
- `解码器已重建 screen_w=1024 screen_h=768 from_w=1280 from_h=720`
- 收工：解出 887 帧 / 丢帧 0 / 首帧 195 ms / 29.0 fps / 4811 kbps
- 当前画幅 1024x768；存帧 1024x768
- 与真机 1024x768 截图：**相关系数 0.9997，平均绝对误差 0.49%**

换代边界上丢几帧是正常的：本轮另一次运行里会话 A 丢了 4 帧（同一次会话 887 帧里），
最终这轮是 0。脚本按「≤ 5」断言并把实际数字打出来，不做「必须 0」的假严格。

顺带修掉的真 bug（本轮的主要代码改动）
--------------------------------------
`resolve_screen` 只在**进程启动**时探一次屏幕尺寸，结果被之后所有会话复用。屏幕在进程活着
的时候变了以后，新会话仍然按旧尺寸进行。真机 journal 原样（修前，01:06:47）：

    视频源结束 frames=0 keyframes=0 bytes=0 device_id=805747189
    视频源 EOF 且分辨率已变，按新尺寸重启 from_w=1024 from_h=768 to_w=1280 to_h=720

即：编码器按 1024x768 去抓一块 1280x720 的屏幕之外并不存在的区域，ffmpeg 当场退出
（0 帧 0 字节），只能等 1 秒探针再重开一遍；控制端这边的连接横幅还会把旧分辨率当成新值。
现在每个会话开头 `session::refresh_screen()` 重探一次（钉死尺寸用配置、合成源按 spec 重抠、
探不到沿用缓存而不是退回 1920x1080 兜底）。修后：

- 每次会话开局打一行 `屏幕尺寸与进程启动时缓存的不同，本会话按新尺寸开始 from_w=… to_w=…`
- 修后 12 分钟 journal 里 `frames=0` 命中 **0**（修前每来一个新会话就有一条）
- 会话 B 的连接横幅直接是 1280x720（不是缓存里的 1024x768）

仍未验
------
- **输入映射器在会话中途换尺寸**：真机上只能验「新会话按新尺寸换算坐标」（会话开局就探对，
  Mapper 一开头就是对的）；「同一条会话里画面换代、坐标也跟着换」这条仍只有本机全链路
  测试（`crates/uulan-client/tests/resize_path.rs` + `resize_host.rs`）。原因是控制端没有
  「同一条会话里既收画面又脚本化发注入」的入口 —— `--inject` 是独立会话，不带视频通道。
- 多显示器 / 副屏热插拔：`xrandr` 上这台机器没有连着的输出，验不了。
- 1920x1080 基线：这台机器当前是 1024x768（机器状态变化，不是回归），所以本轮数字不能直接
  和 2026-10-22 的 1920x1080 队列比；同尺寸下的相关系数（0.9997~0.9999）与当时同水平。

复跑
----
    bash scripts/verify-resolution-follow.sh --device 805747189 --password-file <口令文件>

脚本自己会读当前分辨率、挑一个不同的备选值、验完恢复原值（trap），三分钟内跑完。

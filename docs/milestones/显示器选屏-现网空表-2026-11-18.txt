显示器选屏 —— 现网「空表」分支复跑（2026-11-18）通过：21 通过 / 0 失败 / 0 跳过

11-16 那次真机验收时，C 段（现网降级）走的是「有 1 块已连接输出」的分支：
`[WARN] 显示器 显示器1 不存在（已连接只有 1 块）—— 退回第一块`。

今天例行核机器状态时发现 **VGA-0 也被拔掉了**：

    VGA-0   disconnected primary 1920x1080+0+0
    HDMI-A-0 disconnected

也就是说 X 还在跑 1920x1080 的帧缓冲，但 `xrandr` 里**一块已连接输出都列不出来**。
这正是脚本注释里那条「空表降级」分支的真实形态 —— 之前只有代码路径和口径描述，
没有现场。机器既然变成了这个形态，就顺手复跑一次把它钉住。

## 结果

    scripts/verify-monitor-select-e2e.sh → 21 通过 / 0 失败 / 0 跳过，退出码 0

    C) 真 :0 + 真 xrandr + @1
       PASS --diagnose 退出码 0（WARN 不算 FAIL）
       PASS 显示器件降级为「按整帧缓冲抓」（已连接 0 块）      ← 这次走的是这条
       PASS 没有任何 [FAIL] 项
       PASS 会话不断，存帧尺寸 = 整帧缓冲 1920x1080
       PASS 存帧 vs :0 截图 相关 ≥0.98
    A/B) Xvfb :97 合成双屏的机理断言照旧全过（不受物理插拔影响）

于是两条现网降级分支都有了现场证据：

    已连接 1 块 + 求 @1 → 「显示器1 不存在」→ 退回第一块（2026-11-16）
    已连接 0 块 + 求 @1 → 「按整帧缓冲抓」（2026-11-18）

## 一个方法上的收获

**硬件状态变了，未验分支就可能会自动变成可达分支。** 11-16 我为了跑通 C 段把跳过条件
改成了按「已连接几块」分支，那只是让两条分支**都有机会被执行**；真正让它们都被执行，
靠的是后来机器被拔了显示器。所以每次机器状态有变（插拔、重启、换用户、装 root），
值得回头看一眼「有没有哪条原本纸面上的分支现在能实测了」——这类机会不是自己找上门
就能抓住的，得知道清单上哪条在等这个条件。

## 仍未验（别当已验）

- **物理双屏的 xrandr 布局枚举**：要两块都能点亮的屏。现在这台是一块都没接，
  插 HDMI 只会变成「1 块已连接」（那就是 11-16 已验的形态），要钉这条得接**两块**。
- **热插拔事件本身的跟随**（拔掉/插上后 1 秒内区域自动跟回）：造不出事件源，未验。

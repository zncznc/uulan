窗口帧数协商（M8 第二轮）· 真机验收
2026-11-23 05:00 夜批（开发机 Windows + 真麒麟 192.168.223.15）

一、为什么改
────────────
2026-11-23 01:00 班把「窗口 16 帧 = 1 MiB 在途」在广域网上的代价量成了数：
`scripts/verify-bulk-window-wan-e2e.sh` 11/0/0，RTT 100 ms 时 1 MiB 往返 558 ms、
50 ms 档 377 ms，而同档**裸代理地板**只要 232 / 144 ms —— 多出来的那截就是「窗口 16 帧换一次信用」，
吞吐封顶 ≈ 窗口/RTT。DESIGN 的同节已写明修法：把窗口帧数变成**握手协商值（新字段 + 两端取 min），改常数不算**。
本轮兑现这一条。

二、改了什么（协议向后兼容，PROTO_VERSION 仍 4，中继零改动）
────────────
1. `crates/uulan-protocol/src/msg.rs`
   - `ClientHello.bulk_window_frames: u16`、`HostHelloOk.bulk_window_frames: u16`，
     都是 `#[serde(default)]`，0 = 没声明（老端 / 只想用默认值）。
2. `crates/uulan-bulk/src/lib.rs`
   - `WINDOW_MIN = 1`、`WINDOW_MAX = 96`（96 × 64 KiB = 6 MiB 在途/流，上限由内存账决定）。
   - `negotiate_window(client: (bool, u16), host: (bool, u16)) -> Option<usize>`：
     双方都声明 `bulk_window` 才谈得上；帧数取**较小值**（发送方在途上限必须 ≤ 接收方能缓冲的量）；
     0 按 `STREAM_WINDOW`(16)；最后 `clamp(WINDOW_MIN, WINDOW_MAX)`（对端数据钳而不拒）。
   - 单测 2 条：协商表的对称性/取 min/钳位；协商出的窗口真的落到信用上（2W 帧全到、顺序不乱）。
3. `crates/uulan-host/src/{config.rs,main.rs,session.rs}`
   - 配置项 `bulk_window_frames`（默认 16）；`check()` 越界（<1 或 >96，含 0）**让服务起不来**，
     错误里点名配置项；`--bulk-window <帧数>` 命令行覆盖并落盘（同 `--mic-sink` 的做法）。
   - `HelloOk` 报本端值；会话 mux 用协商值；日志多两个字段：
     `window=Some(n) client_frames=… host_frames=…`。
   - 单测 2 处：老配置（无该字段）按 16 读入；越界/0 必须报错、边界 1 与 96 合法。
4. `crates/uulan-client/src/{connect.rs,forward.rs,main.rs}`
   - `--bulk-window <帧数>`（1..=96，写坏当场 bail）→ 只经 `UULAN_BULK_WINDOW` 环境变量传进
     `connect()`（同 OS 模式凭据的做法，argv 里不多出一种形态）；`ClientHello` 报本端值。
   - `Connected.bulk_window: Option<usize>`（协商结果）；`Forwarder::start(.., window: Option<usize>)`
     —— 调用点不再自己算帧数。
   - 转发会话启动时打一行 `按流窗口 : Some(n)`（可 grep，台架据此判「两端谈成了几帧」）。

四、真机台架：`scripts/verify-bulk-window-negotiation-e2e.sh`（新脚本）
────────────
台架形态：真机侧独立中继（:21997）+ echo 目标（:21998）+ 合成采集源被控端（lavfi，不抢 CPU），
控制端在开发机（工作区外 exe）。每个阶段重启被控端以换窗口值；判据同时要**两端各自算出的数对上**。

  阶段 A（两端都写 64）：控制端 `按流窗口 : Some(64)`；被控端
    `window=Some(64) client_frames=64 host_frames=64`；1 MiB 全双工 40 / 25 ms，sha256 一致。
  阶段 B（被控端 64、控制端 24）：两端都是 `Some(24)`；1 MiB 44 / 38 ms，sha256 一致
    —— 取 min 的口径在线上真的生效（不是只在一端算）。
  阶段 C（控制端不声明，等同老端）：两端都是 `Some(16)`；1 MiB 40 / 33 ms，sha256 一致
    —— 不被对面的 64 拉大，老行为不变。
  阶段 D（50 ms 单向延迟代理，4 MiB 全双工）：
    16 帧：857 ms / 859 ms（两轮）
    64 帧：340 ms / 318 ms（两轮）
    提速 60% / 63%；四条流 sha256 全一致（放大窗口不是靠丢字节换吞吐）。

  阶段 E（**新控制端 + 旧被控端二进制**，真老端兼容）：用换下来的备份件
    `~/.local/uulan/bin/uulan-host.bak-20261123_051410` 起台架（它根本不认识 `bulk_window_frames`，
    也没有 `--bulk-window` 参数）；新控制端照样报 64 → 旧被控端按 16 开窗口、控制端算 min(64,16)=16，
    两端都是 `Some(16)`，1 MiB 37 ms sha256 一致。这条是「新端不能把老端带沟里」的直接证据。

结果：**14 通过 / 0 失败 / 0 跳过 × 两轮**（A–D）；带阶段 E 的第三轮 **17/0/0**。

六、撤法
────────────
- 真机二进制：`mv -f ~/.local/uulan/bin/uulan-host.bak-20261123_051410 ~/.local/uulan/bin/uulan-host`
  → `systemctl --user kill -s KILL uulan-host`（Restart=always 拉起旧件）。
- 源码：`~/.local/uulan/src.old.<TS>`（本轮 TS=20261123_050828）换回 `src` 即可，`target/` 缓存已随新源码保留。
- 配置：若用过 `--bulk-window`，`host.json` 里的 `bulk_window_frames` 会被写成那个值；改回 16 或删掉该键
  （缺键 = 默认 16）。
- 协议/代码：字段是 `serde(default)`，直接回退旧二进制即可，不需要成对降级；中继从没改过。

七、仍未验
────────────
- 多信宿音频争用（这台机器只有一块声卡）。
- 窗口**上限 96** 是内存账定的上限，不是测出来的最优点；更大的值没有台架结论。
- 延迟台架只加「控制端↔中继」一腿，真实双端广域网（两端都慢）未验 —— RTT 是下界、吞吐是上界。

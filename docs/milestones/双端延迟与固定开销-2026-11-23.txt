双端延迟（两跳都慢）下的按流窗口与「一次操作到底花在哪」 —— 2026-11-23 22:00 班
==============================================================================

一、这一轮要回答什么、口径是什么
────────────────────────────
`docs/milestones/多控制端并发与会话泄漏-真机-2026-11-23.txt` 与 `窗口帧数协商-…-2026-11-23.txt`
里的高延迟台架都只把延迟加在**控制端 ↔ 中继**一腿，报告里必须写「RTT 是下界、吞吐是上界」。
真实部署是两端都慢（控制端 → 中继 → 被控端）。本轮把**两个**用户态延迟代理串进同一条链路
（控制端腿 + 被控端腿），造出「路程 RTT = 4d」的形态，回答两个问题：

  A. 协商出来的在途量（16 帧 = 1 MiB / 64 帧 = 4 MiB）在两跳链路上是否仍按「窗口 / RTT」给吞吐；
  B. 文件传输（unwindowed fs）在同样的双程延迟下会不会明显落后于端口映射 —— 会不会值得给 fs 接窗口。

**口径（报告里必须照抄）**：两个代理都在**同一台机器**上（Windows 开发机 loopback），
所以这条台架测的是「窗口/RTT 模型在两跳链路上成不成立」——**不是**真实广域网：
没有丢包、没有带宽上限、没有抖动。不过这次**没有真机参与**（原因见第七节），
被控端是中继旁边同一台开发机上的 `uulan-host`（lavfi 合成源 640x360@10fps）。

二、台架
────────────
新脚本 `scripts/verify-bulk-window-dual-leg-e2e.sh`（本机跑，无参数）：

- 拓扑：`控制端 --(代理A :23361, d ms)--> 中继 :21981 --(代理B :23362, d ms)--> 被控端`，
  echo 目标在 `:21982`，控制端本地监听 `:21983`。被控端走 `--server 127.0.0.1:23362` 注册，
  控制端走 `--server 127.0.0.1:23361`；d=0 时两侧都直连中继（对照组）。
- 每个 (d, w) 组合重起被控端（`--bulk-window w`），控制端 `--bulk-window w`，
  跑 1 MiB + 4 MiB 全双工（`--forward` + 自写 echo probe，比 sha256）。
- 额外量一条 **`--ls :/`**（只用控制通道，不含任何 bulk 数据）的端到端耗时 =
  「建会话 + 握手」的固定开销，用来把 fs 的总耗时拆成「建会话」与「数据段」。
- 延迟档 `0 / 25 / 50 ms`（每腿单向）⇒ 路程 RTT ≈ 0 / 100 / 200 ms；窗口 `16 / 64` 帧。

三、结果（两轮，均为 28 通过 / 0 失败 / 0 跳过）
────────────────────────────
轮 1（22:3x）：

  档位           1 MiB(ms)  4 MiB(ms)  1MiB MB/s  4MiB MB/s  模型(窗口/RTT)  实测/模型
  d0-w16             12        49      87.38     85.60        0.00          -
  d0-w64             29        43      36.16     97.54        0.00          -
  d25-w16           174       566       6.03      7.41       10.49        0.71
  d25-w64           183       211       5.73     19.88       41.94        0.47
  d50-w16           562      1776       1.87      2.36        5.24        0.45
  d50-w64           383       583       2.74      7.19       20.97        0.34

轮 2（23:0x）：

  d25-w16           189       576       5.55      7.28       10.49        0.69
  d25-w64           139       209       7.54     20.07       41.94        0.48
  d50-w16           559      1709       1.88      2.45        5.24        0.47
  d50-w64           376       571       2.79      7.35       20.97        0.35

- **4 MiB 的窗口收益在两跳链路上照样成立**：d=50（路程 RTT 200 ms）1776/1709 ms →
  583/571 ms（**3.0 倍**）；d=25（100 ms）566/576 ms → 211/209 ms（2.7 倍）。
- 1 MiB 的收益小得多（562→383 / 559→376 ms，约 1.5 倍）：1 MiB 本身就等于 16 帧窗口，
  窗口放大之后瓶颈从「在途量」变成了「首尾各一次 RTT + 建会话」，所以别拿 1 MiB 判窗口。
- 实测/模型 = 0.34~0.48（4 MiB）：模型是**上界**，缺口来自单条 TCP 的窗口增长、
  代理本身的读写调度、以及往返途中每一跳的调度开销 —— 这条台架只能证明比例关系，不能当带宽预算。

四、关键发现①：一次操作的固定开销 ≈ 6 个 RTT + 0.35 s 本机开销
────────────────────────────
`--ls :/`（只走控制通道，不传任何 bulk 数据）的端到端耗时：

  轮 1：d=0 357/392 ms，d=25 1010/1007 ms，d=50 1517/1539 ms
  轮 2：d=0 366/342 ms，d=25 963/998 ms，d=50 1554/1569 ms

扣掉 d=0 的本机固定开销（起进程 + 本地 IPC，约 0.35 s）之后：
  (1010−357)/100 ≈ **6.5 个 RTT**；(1517−357)/200 ≈ **5.8 个 RTT**。
对照握手代码数一数就对得上：TCP connect（1）+ CryptoHello/HelloOk（1）+ PakeInit/PakeResp（1）
+ Hello/HelloOk（1）+ Auth/AuthOk（1）+ 中继会话拨号与四条通道 RelayReady（1~2）。

**工程含义**：任何「一次性 CLI 动作」（`--ls` / `--put` / `--get` / `--terms` / `--power`）
在 200 ms 路程 RTT 的链路上，光建会话就要 1.5 s。要改善，动的是**握手的往返数**
（比如把 PAKE 与 Hello 并成一趟、或让中继会话与加密握手并行），不是 bulk 窗口。

五、关键发现②：fs 并不慢，慢的是建会话 —— 但有两个反例要说清
────────────────────────────
fs 4 MiB put/get 的总耗时（轮 1 / 轮 2）：

  d=0  ：380/414、416/391 ms（轮 1）；429/412、415/400 ms（轮 2）
  d=25 ：1107/1066、1137/988 ms  ；1051/1005、1096/1024 ms
  d=50 ：1841/1628、1752/1598 ms；1746/1654、1769/1586 ms

与同档的固定开销（1517~1569 ms）一比：**d=50 时 fs 的「数据段」只有 0.2~0.3 s**。
把 4 MiB 换成 16 MiB 复跑（d=50 / 窗口 64）：**put 1843 ms / get 1697 ms** ——
和 4 MiB 几乎一模一样。也就是说 fs 的吞吐并不是 2.3 MB/s，而是「**数据段 0.3 s 上下，
剩下全是建会话**」；按数据段算 16 MiB 已到 40~50 MiB/s。

两条被实测否掉的猜测（写下来免得下一轮再试）：
- **不是应用层接收队列**：把 `uulan_bulk::STREAM_QUEUE` 从 8 临时改成 64（fs 走的正是这条
  unwindowed 队列）后复跑 d=50 / w=64：put 1805 ms / get 1598 ms（改前 1752/1598）——
  **一个字节都没快**。所以「给 fs 加大缓冲就能提速」是错的，别再往这条路上改。
- **不是窗口没生效**：被控端与客户端两侧都打印出 `window=Some(64) client_frames=64 host_frames=64`，
  且 4 MiB 在同样的链路上确实从 1776 ms 掉到 583 ms。fs 不享受窗口，是因为它按设计走
  `register_unwindowed`（控制端 `fsx` 是独占整条连接直写、不读信用）。

结论：**fs 的短传输瓶颈是会话建立，不是带宽**；真要再快，得让 `--ls/--put/--get` 复用一条
常驻会话（或减少握手往返），这与窗口无关。

六、判据器自己的 bug（本轮踩到，已修）
────────────────────────────
第一版把「被控端协商结果」的断言放在 `start_host` 里：那条 `bulk 多路复用（按流窗口）
window=Some(n)` 是**被控端在会话建立时**才打印的，而 `start_host` 返回时还没有任何会话 ——
于是 6 个组合全报「（没有 window=Some 行）」，一次跑出 6 个假红。
修法：断言挪到控制端跑完之后（`check_host_window`），并把提速判据从 1 MiB 改成 4 MiB
（1 MiB 放大窗口后收益被建会话吃掉，写 1.4 倍门槛必然假红）。
教训与既有那几条同族：**判据的时机和判据的值一样是判据的一部分**。

七、真机状态：本轮没做成真机验收（如实写）
────────────────────────────
- `ssh kylin` 超时；二层真相取 `netsh -c i i show neighbors 7`：只有 192.168.223.1（网关）、
  .10、.18、.22 带真实 MAC，**麒麟的 1c:83:41:8b:97:97 全表缺席**，.15 是「不完整/无法访问」。
- 控制探针 192.168.223.99:22 反复「连上、无 banner」= 本机透明代理在发假应答
  （sing-box 16:24 起在跑，TUN 又被打开了），所以**这一轮任何 TCP 结论都作废**；
  只有 ARP 表可信。
- 按 skill 的 WoL 凭据（MAC 1c:83:41:8b:97:97）从 22:06 起每 45 s 广播魔术包，
  到 22:1x 仍无回音（ARP 里始终不出现该 MAC）——机器是关机/断电，或 WoL 未启用。
- 因此：**本轮没有真机验收，也没有把正式被控端换成新二进制**（本轮产品代码零改动，
  只是新增一条台架脚本，不需要换）。

双端延迟（两跳都慢）下的按流窗口与「一次操作到底花在哪」 —— 2026-11-23 22:00 班
==============================================================================

一、这一轮要回答什么、口径是什么
────────────────────────────
`docs/milestones/多控制端并发与会话泄漏-真机-2026-11-23.txt` 与 `窗口帧数协商-…-2026-11-23.txt`
里的高延迟台架都只把延迟加在**控制端 ↔ 中继**一腿，报告里必须写「RTT 是下界、吞吐是上界」。
真实部署是两端都慢（控制端 → 中继 → 被控端）。本轮把**两个**用户态延迟代理串进同一条链路
（控制端腿 + 被控端腿），造出「路程 RTT = 4d」的形态，回答两个问题：

  A. 协商出来的在途量（16 帧 = 1 MiB / 64 帧 = 4 MiB）在两跳链路上是否仍按「窗口 / RTT」给吞吐；
  B. 文件传输（unwindowed fs）在同样的双程延迟下会不会明显落后于端口映射 —— 会不会值得给 fs 接窗口。

**口径（报告里必须照抄）**：两个代理都在**同一台机器**上（Windows 开发机 loopback），
所以这条台架测的是「窗口/RTT 模型在两跳链路上成不成立」——**不是**真实广域网：
没有丢包、没有带宽上限、没有抖动。这次**没有真机参与**（原因见第七节），
被控端是中继旁边同一台开发机上的 `uulan-host`（lavfi 合成源 640x360@10fps）。

二、台架
────────────
新脚本 `scripts/verify-bulk-window-dual-leg-e2e.sh`（本机跑，无参数）：

- 拓扑：`控制端 --(代理A :23361, d ms)--> 中继 :21981 --(代理B :23362, d ms)--> 被控端`，
  echo 目标在 `:21982`，控制端本地监听 `:21983`。被控端走 `--server 127.0.0.1:23362` 注册，
  控制端走 `--server 127.0.0.1:23361`；d=0 时两侧都直连中继（对照组）。
- 每个 (d, w) 组合重起被控端（`--bulk-window w`），控制端 `--bulk-window w`，
  跑 1 MiB + 4 MiB 全双工（`--forward` + 自写 echo probe，比 sha256）。
- 额外量一条 **`--ls :/`**（只用控制通道，不含任何 bulk 数据）的端到端耗时 =
  「建会话 + 握手」的固定开销，用来把 fs 的总耗时拆成「建会话」与「数据段」。
- 延迟档 `0 / 25 / 50 ms`（每腿单向）⇒ 路程 RTT ≈ 0 / 100 / 200 ms；窗口 `16 / 64` 帧。
- 二进制一律从 `target/release` 拷到工作区外（`D:/uulan-bin/dual-leg-<TS>`）再跑；
  下面两轮都是**在把源码恢复成 HEAD 并重新 `cargo build --release` 之后**跑的（见第六节第 3 条）。

- **4 MiB 的窗口收益在两跳链路上照样成立**：d=50（路程 RTT 200 ms）**1764/1685 ms → 574/575 ms
  （2.9~3.1 倍）**，两轮稳定；d=25（100 ms）562/562 → 323/213 ms（1.7~2.7 倍）。
  d25-w64 这一格在四轮里跑过 213/209/211/323 ms —— 窗口越大，单次测量的方差越受代理调度影响，
  报数看绝对值，别把倍数当常数。
- **1 MiB 的收益小得多**（d=50：567/560 → 375/393 ms，约 1.5 倍）：1 MiB 本身就等于 16 帧窗口，
  放大窗口之后瓶颈从「在途量」变成「首尾各一次 RTT + 建会话」—— **判窗口收益别用 1 MiB**。
- 实测/模型 = 0.31~0.48（4 MiB）：模型是**上界**，缺口来自单条 TCP 的窗口增长、
  代理本身的读写调度、以及每一跳的调度开销 —— 这条台架只能证明比例关系，不能当带宽预算。

四、关键发现①：一次操作的固定开销 ≈ 6 个 RTT + 0.4 s 本机开销
────────────────────────────
`--ls :/`（只走控制通道，不传任何 bulk 数据）的端到端耗时（四轮，含早先两次）：

  轮 1：d=0 396/412 ms，d=25 995/988 ms，d=50 1510/1534 ms
  轮 2：d=0 378/402 ms，d=25 992/1015 ms，d=50 1615/1549 ms
  （更早两轮同量级：342~392 / 963~1010 / 1517~1569 ms）

扣掉 d=0 的本机固定开销（起进程 + 本地 IPC，0.34~0.41 s）之后：
  (995−396)/100 ≈ **6.0 个 RTT**；(1510−396)/200 ≈ **5.6 个 RTT**。
对照握手代码数一数就对得上：TCP connect（1）+ CryptoHello/HelloOk（1）+ PakeInit/PakeResp（1）
+ Hello/HelloOk（1）+ Auth/AuthOk（1）+ 中继会话拨号与四条通道 RelayReady（1~2）。

**工程含义**：任何「一次性 CLI 动作」（`--ls` / `--put` / `--get` / `--terms` / `--power`）
在 200 ms 路程 RTT 的链路上，光建会话就要 1.5 s。要改善，动的是**握手的往返数**
（比如把 PAKE 与 Hello 并成一趟、或让中继会话与加密握手并行），不是 bulk 窗口。

五、关键发现②：fs 并不慢，慢的是建会话 —— 但有两个被实测否掉的猜测要说清
────────────────────────────
fs 4 MiB put/get 的总耗时（轮 1 / 轮 2）：

  d=0  ：460/403、391/392 ms
  d=25 ：1106/988、1106/1035 ms
  d=50 ：1745/1621、1803/1583 ms
  （更早两轮同量级：380~429 / 414；1107~1137 / 988~1066；1752~1841 / 1598~1654）

与同档的固定开销（1500~1600 ms）一比：**d=50 时 fs 的「数据段」只有 0.2~0.3 s**。
把 4 MiB 换成 16 MiB 复跑（d=50 / 窗口 64）：**put 1843 ms / get 1697 ms** ——
和 4 MiB 几乎一模一样。也就是说 fs 的吞吐并不是 2.3 MB/s，而是「**数据段 0.3 s 上下，
剩下全是建会话**」；按数据段算 16 MiB 已到 40~50 MiB/s。

两条被实测否掉的猜测（写下来免得下一轮再试）：
- **不是应用层接收队列**：把 `uulan_bulk::STREAM_QUEUE` 从 8 临时改成 64（fs 走的正是这条
  unwindowed 队列）后复跑 d=50 / w=64：put 1805 ms / get 1598 ms（改前 1752/1598）——
  **一个字节都没快**。所以「给 fs 加大缓冲就能提速」是错的，别再往这条路上改。
- **不是窗口没生效**：被控端与客户端两侧都打印出 `window=Some(64) client_frames=64 host_frames=64`，
  且 4 MiB 在同样的链路上确实从 1764 ms 掉到 574 ms。fs 不享受窗口，是因为它按设计走
  `register_unwindowed`（控制端 `fsx` 是独占整条连接直写、不读信用）。

结论：**fs 的短传输瓶颈是会话建立，不是带宽**；真要再快，得让 `--ls/--put/--get` 复用一条
常驻会话（或减少握手往返），这与窗口无关。

六、判据器自己的两个问题 + 一次源码回退（都记下来）
────────────────────────────
1. **判据的时机也是判据**：第一版把「被控端协商结果」的断言放在 `start_host` 里 —— 那条
   `bulk 多路复用（按流窗口） window=Some(n)` 是**被控端在会话建立时**才打印的，`start_host`
   返回时还没有任何会话，于是 6 个组合全报「（没有 window=Some 行）」（一次跑出 6 个假红）。
   修法：断言挪到控制端跑完之后（`check_host_window`）。
2. **提速判据不能用 1 MiB**：1 MiB 放大窗口后收益被建会话吃掉（1.14~2.1 倍、方差大），
   写 1.4 倍门槛必然假红；改用 4 MiB（两轮 2.9~3.1 倍）。
3. **源码回退之后必须重编再跑**：为了做第五节的实验，`STREAM_QUEUE` 曾被临时改成 64 并重编；
   回退源码后 `target/release` 里仍是实验版二进制，而紧接着跑的两轮「正式」数据其实跑在实验版上
   —— 发现后**恢复源码 + 重编 + 两轮全部重跑**，本文第三节的数字是重跑那一版（两份数据几乎一致，
   因为这条参数对窗口流与 fs 都没影响；但这个习惯不能省：**交付的数字必须来自 HEAD 的二进制**）。

  只是新增一条台架脚本 + 文档，不需要换）。

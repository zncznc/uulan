二、真 bug：直连「收齐四条通道」的 5 秒期限算错了起算点
  现象（本机 2026-11-20 01:3x，真 exe，直连一轮会话进行中）被控端日志每 5 秒一条：
      DEBUG uulan_host: 直连半途而废 error=连接超时（5s）
      DEBUG uulan_host: 直连半途而废 error=连接超时（5s）
      ...
  这两条同时是噪声和真风险：
    · 「半途而废」这个词在说「有人来了、没连完」，而实际是**没人来连**（机器闲着、
      或已经有一条会话在跑）。真事件（端口扫描、只拨一条就跑）会被这条假事件埋掉；
    · 更坏的后果是**丢连接**：旧实现的 5 秒期限从「回到 `accept()`」起算，而控制端要
      拨四条通道。恰好在窗口末尾（第 4.9 秒）连进来的控制端只剩 0.1 秒去拨齐另外三条 ——
      它会被判「半途而废」，而用户那边看到的是「连不上」，与网络故障无从分辨。
  修法（`crates/uulan-protocol/src/rvclient.rs`）：第一条通道**无限等**；四条通道的收齐期限
  从「第一条到达」起算，只管「来了一条、另三条迟迟不到」。四条收齐才回去接下一轮，
  所以空闲端口不再被自己每 5 秒唤醒一次，5 秒超时的语义也回到了它本来的意思。
  回归判据：`crates/uulan-protocol/tests/direct.rs::an_idle_port_is_not_a_half_dialed_visitor`
  —— 空闲 6 秒后 `direct_accept_all` 不许已结束（旧实现在第 5 秒就返回），
  随后才拨号的四条必须正常收齐并保持通道映射正确。
  **反向验证过**：只在旧实现上跑这条测试 = 真红
  （`assertion failed: !host.is_finished()`，3 passed / 1 failed，退出码 101）。
  真 exe 复验：
    · 空闲 25 秒（新二进制）：`直连半途而废` **0 次**（旧二进制同一场景每 5 秒一条，
      轮内实测 2 条/10 秒）；
    · 会话中途硬杀控制端（Toolhelp32 枚举拿真实 Windows PID + `TerminateProcess`）：
      日志仍如实记 `直连会话出错 error=读控制帧失败: io: 远程主机强迫关闭了一个现有的连接。 (os error 10054)`
      —— 顺带澄清 11-19 归档里那条「直连会话出错 error=（Display 为空）」：**本轮复现不出空串**，
      可控复现路径下错误文本总是带上底层 io 原因。那条记录按实测更正。

三、面板补「对方怎么连我（当面念这几行）」（`crates/uulan-gui/src/local.rs`）
  这一屏的唯一用途是**念给对面听**，而 11-19 的改动把「念什么」变了（可能只认系统账户）
  却没落到屏上：坐着的人会念临时码，而对面走的是 OS 通道，结果是「密码不正确」。
  现在从 `host.json` 读 `auth_os` / `pam.enabled` / `pam.allow_users`，显示：
    · 认证方式：系统账户（用户名 + 该账户在本机的登录密码）／访问口令与一次性临时码；
    · 直连：`<本机 IP>:21117` —— 端口**真探一次**（`127.0.0.1:21117` 连得上才算「在听」，
      `reload()` 时探、不是每帧探），没在听就直说「只能经中继连」，绝不给出一个像能用的地址；
    · OS 模式的可用账户名；两种静默配错（没开 PAM / 名单为空）**红字**告警。
  文字全在纯函数 `connect_hint(info, listen_open, ips)` 里，5 条单测：
    pake 形态指口令与临时码 / os 形态列出账户并说明「密码就是登录密码」/
    没开 PAM 告警 / 名单为空告警 / 没在听不许报地址、没有 IP 不许编地址。

四点五、面板那一块的**机器可读**证据（不是「我看了一眼」）
  本机 Windows 上把面板拉起来（`HOME`/`LOCALAPPDATA` 指向台架目录，喂一份形态与真机同构的
  `host.json`：`auth_os=true` + `pam.enabled=true` + `allow_users=["mis","ops"]`），
  用 UIA（`computer_use` 的 ax 树）读回的真实控件文本：
      对方怎么连我（当面念这几行）
      认证方式：系统账户（用户名 + 该账户在本机的登录密码）
      直连端口没在听（这台是以 --no-listen 起的）—— 只能经中继连
      系统账户：mis / ops（密码就是各账户在本机的登录密码，不用另记口令）
  三种形态各读一次：PAKE 形态（未配 auth_os）→ 认证方式那行变成「访问口令 / 一次性临时码」；
  OS + 名单为空 → 红字告警「名单为空：谁都不许登录」；OS 名单正常 → 无告警。
  ⚠ 顺带记一个**这台机器上的 GUI 取证坑**：这个 eframe 窗口是 `WS_EX_LAYERED`，
  `PrintWindow` 抓到的是空白客户区（UIA 树却是完整的、文字都在），所以
  「窗口内容对不对」在这台机器上只能靠 UIA/控件树判，不能靠像素截图 ——
  否则会把「能显示」误判成「白屏」。这条对以后验面板同样适用。

五、真机：本轮不在二层（如实记录，真机验收未做）
  01:0x / 01:5x 两次复核，结论一致 —— **机器不在 192.168.223.0/24 上**：
    · 控制探针 `192.168.223.99:22` 能「连上」→ 本机透明代理仍在发假应答，所以**端口扫描作废**；

      广播唤醒（`ping 192.168.223.255`）后仍无 MAC；
    · 全表搜麒麟 MAC `1c:83:41:8b:97:97` **零命中**（同表另有 13 台带 MAC 的活人，
      所以邻居表本身是好的，缺席是 .15 自己的事）；

  但它与本轮新增的面板/窗口改动无关。

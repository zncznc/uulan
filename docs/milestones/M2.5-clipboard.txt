uulan 里程碑 M2.5（剪贴板部分）—— 文本双向已接上，X11 后端待真机验 🔄

【本轮做了什么】
  新增 crate crates/uulan-clip（与平台无关的去重状态机 + 两个真实后端，不引第三方 crate）：
    lib.rs  ClipSync：防回声（内容指纹，换行归一化）、大小上限、绝不传播「剪贴板被清空」
    win.rs  Win32 后端：user32/kernel32 直接 FFI，CF_UNICODETEXT，打开剪贴板带重试
    x11.rs  X11 后端：CLIPBOARD/PRIMARY selection，读取走 XConvertSelection + INCR 分段，
           写入由独立 service 线程当 owner 回答 SelectionRequest
  被控端 crates/uulan-host/src/session.rs：
    控制通道拆成读/写两半（select：读帧 + 500ms 剪贴板轮询）
    C2H::Clip → 写本地剪贴板；本地变化 → H2C::Clip
    HelloOk 只在后端真的可用时才声明 Cap::Clipboard
  控制端 crates/uulan-client/src/control.rs：
    ControlLink::start_with_clipboard；同一个任务里 select（上报队列 / 读回报 / 轮询剪贴板）
    H2C::Clip → 写本机剪贴板；本机变化 → C2H::Clip
  新增 --no-clipboard 开关；收工统计多打一行「剪贴板同步：发送 N / 接收 M（本机写入失败 K）」

【已经验 / 只能在真麒麟上验】
  已验（本机可复现）：
    · 去重、防回声（含 Windows CRLF 改写）、超限不截断、空内容不发
    · 「读不到 ≠ 被清空」这条（X11 超时要靠它保命）
    · 基线规则：会话建立那一刻的内容不外推
    · Win32 后端的真实读写（UTF-16、GB 级长度、中文、emoji）
    · 两端全链路的两个方向（真 wire）
  只能真麒麟验：
    · X11 selection 的 set/get 全流程（XConvertSelection、SelectionNotify、INCR 分段）
    · 别的程序（浏览器/编辑器）粘贴我们写的内容是什么效果
    · UKUI 上 PRIMARY 中键粘贴的实际行为
    · 剪贴板所有者进程退出后内容失效，在真机上用户是否觉得突兀
  **没有假装验过的**：x11.rs 里每一个 Xlib 调用在本机一行都没执行过。

【已知限制（照实写）】
  · 只同步文本；图片、文件列表（text/uri-list）不同步
  · 不传播「剪贴板被清空」
  · 单条上限 192 KiB（X11 单请求约 256 KiB，第一版不写 INCR 发送）
  · 被控端进程退出后，它在 X11 里持有的剪贴板内容随之消失（X11 固有行为）

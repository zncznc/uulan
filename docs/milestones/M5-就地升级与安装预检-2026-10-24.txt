============================================================
一、这一轮改了什么
============================================================

`deploy/install.sh` 的「预检」原来不完整：`uulan-wait-x` 的查找发生在
`install -d $PREFIX`、`$PREFIX/bin/uulan-host`、`$PREFIX/bin/uulan-server` **之后**。
也就是说，这是最后一个「先落盘、后失败」的输入 —— 真机上第一次从离线包装就断在这里，
留下一个只有 host+server 的半装前缀：`systemctl --user status` 显示 failed，而安装输出
看起来只是「中途报了个错」。

本轮把 WAIT_X 的查找（三种布局：`deploy/uulan-wait-x.sh`、`bin/uulan-wait-x`、
`bin/uulan-wait-x.sh`）移进预检段，紧跟「单元模板存在」那条检查，缺它就 `die`，
prefix 一个字节都不写。规矩写进脚本注释：**所有输入先验完，再动磁盘**。

新增 `scripts/verify-install-preflight.sh`：把这条规矩变成可重复的断言。
做法是「假 getent + 假 systemctl + 假 loginctl + 沙箱家目录 + 假二进制」，
于是整个安装脚本可以在临时目录里跑，不碰真实 systemd 用户单元、不碰真实安装。
四条失败路径都断言「退出码非 0 **且 prefix 目录未被创建**」：
缺 `uulan-host` / 缺 `uulan-server` / 缺 `uulan-wait-x` / 缺单元模板；
再跑一条正常路径，断言三个二进制落盘、中继单元写进了「目标用户」的家目录、摘要里写出 prefix。

四、仍未验（照实写）
============================================================

- **Windows ↔ 麒麟剪贴板整链**：这个 cron 会话拿不到 Windows 剪贴板 ——
  直接调 Win32 `OpenClipboard` 返回错误 5（拒访问），PowerShell 的 `Get-Clipboard` 同样失败。
  ⚠ 顺带查明一个**观察得到的实现事实**（本轮读代码确认，没有改它）：
  `uulan_clip` 的 Win32 后端 `available()` **恒返回 true**（`crates/uulan-clip/src/win.rs:84`），
  它只表示「这个平台有后端」，不代表当下真的能开剪贴板。于是这种会话里控制端会照样
  声明 Clipboard 能力，而被控端推过来的内容在本地读/写都会失败 —— 表现为**静默不同步**
  （headless 模式的统计块也不打印剪贴板那行），正是这个 crate 的注释里说的
  「静默吞掉是最难查的一类失败」。要不要把 `available()` 改成真探一次 OpenClipboard 是个取舍：
  剪贴板是全局锁，别的程序正占着时会误判成「没有后端」，而能力是在会话开始时声明一次的。
  这条留给有人守着的时候改，顺带把「读不到」也计入 errors。
  X11 侧（owner/requestor 双向）已于 2026-10-23 用独立 X 客户端验过，缺的只是 Windows 这一端。
- **:0 真实桌面上的打字/拖拽**：`xdotool getwindowfocus getwindowname` 仍是
  `ukui-screensaver-dialog`（锁屏），注入只会打进锁屏，不去碰。
- **M5 整机重启后的自启**：`sudo -n` 在真机上要口令，`systemctl reboot` 走 polkit 也要认证，
  无人值守的夜里不能重启那台机器（也不该动别人的桌面会话）。
- **root 系统装路径**（/opt/uulan）：同上，没有 sudo 口令。
- **Linux 控制端（麒麟上当控制端）**：真机上编不了 `uulan-client`
  （winit/softbuffer 的 X11 后端要 `x11.pc`，随 `libx11-dev` 一起来，而麒麟源里装不上）。
- **PAKE**（防主动 MITM 离线撞口令）：仍是最主要的 M6 缺口，未动。

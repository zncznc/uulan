────────────────────────────────────────────────────────────────
一、为什么做这一项

M5 之后现场要问的第一个问题不是「能不能连上」，而是「要连的那台叫什么 ID」。
在这之前唯一的答案是走到机器跟前执行 `bash ~/.local/uulan/run.sh status` 抄 9 位数字；
几十台机器的时候这一步比装机本身还烦。中继其实**早就知道**答案（注册表 + 台账），
只是没有一条消息去问它 —— `ToServer::Query` 只答「某一台在不在线」。

所以这一项是「把中继已经知道的东西开一个口子」，不是新建一套设备管理。

────────────────────────────────────────────────────────────────
二、做法

1) 协议（crates/uulan-protocol/src/rv.rs）
   `ToServer::ListDevices`（无参数）→ `ToEndpoint::DeviceList{devices: Vec<DeviceEntry>}`；
   `DeviceEntry { device_id, name, online, idle_s: Option<u64> }`。
   - `idle_s` 只在**在线**时有值（距上次心跳的秒数）；离线的没有可比时钟，给 None，
     不编一个「很久以前」。字段带 `serde(default)` 且 skip_serializing_if，
     所以「没有 idle_s 的目录」也能解析。
   - 新增 `ErrCode::Denied`：和 `Internal` 分开，才能让控制端说「这台中继没开目录」
     而不是「服务端内部错误」。

2) 中继（crates/uulan-server）
   - `Server::inventory_at(devices, book, now)` 是**纯函数**：在线判定 + 台账补全 + 按 ID 排序。
     `now` 由调用方给，所以「沉默超过 TTL」能用假时间测，不用真睡 45 秒。
   - 在线判据与 `sweep` **完全一致**：`!tx.is_closed() && !device_is_stale(last_seen, now)`。
     两处不一致会变成「列表说在线、连过去说离线」—— 这种 bug 在真机上极难定位。
   - 名字优先级：注册表（设备自报的显示名）> 台账（曾经登记过的旧名字）。
   - `Server::new_with_list(state, allow_list)`；`new()` 保持默认开放（老调用点零改动），
     CLI 的 `--no-list` 走前者。**构造期定死**而不是运行期开关：字段在 `Arc<Inner>` 里，
     共享出去就改不动，而「一台中继开不开目录」本来就是部署决策。

3) 控制端（crates/uulan-client）
   - `--devices` 在 `parse_args` 里**提前返回**：不要求 `--device`、不要求口令 ——
     它的用途正是「我还不知道该填哪个 ID」。
   - `format_device_list()` 是纯函数（能 `cargo test`）：空目录印一句话，不印「在线 0」的表头；
     离线条目只写「离线」，绝不出现「空闲 0s」（那读起来像刚心跳过）。
   - `--json` 复用既有开关，输出 `Vec<DeviceEntry>`。

两个服务 active，host MainPID 2334355、用原设备 ID 上线。

① Windows 控制端（HEAD release，拷到工作区外跑）：
   `--devices` →
     中继 192.168.223.15:21116：1 台设备（在线 1）
       805747189  麒麟真机  在线  空闲 0s

   文本形式与 JSON 各跑两次，内容一致（第一次空闲 0s、JSON 那次 5s —— 心跳 10 秒一次，

③ `--no-list`（真机上另起临时中继，用**麒麟自己编的客户端**，脚本 `devlist-check.py`）：

     「这台中继没有开放设备目录（服务端用 --no-list 关掉了）」；`--json` 同样 rc=1。
   - `127.0.0.1:21997`（默认开放、还没设备注册）：rc=0、「设备目录是空的（还没有被控端注册过）」；

   两个临时中继验完即 terminate，不留后台进程。

五、附：本轮顺带做的三项稳定性观测（与设备目录无关，但没有单独的归档）

1) 15 分钟长连接 soak（`--headless --seconds 900`，Windows 控制端 → 真机被控端）：
   收到 AU 26998 / 解出 26993 / **丢帧 0** / 首帧 232 ms / 平均码率 9801 kbps /
   共传 1102558761 字节（1.03 GiB）/ **30.0 fps 稳到最后一秒** /
   被控端自报 30.00 fps / 会话 1 条 / 解码器重建 0 次 / 全程 0 次重连。
   被控端 `VmRSS` 每 2 分 50 秒采一次：9532 → 15108 → 15108 → 15108 → 15108 → 15108 kB
   （首采之后的四次完全相同：编码器缓冲一次性到位，之后不涨）。

2) 5 分钟 soak 同时采两侧内存（`soak2.py`）：
      t(s)   控制端 RSS(KB)   被控端 VmRSS(KB)   已解帧
        0        20708            12816            1
       50        30228            16788         1500
      100        28192            16788         3000
      150        28488            16788         4500
      200        20732            16788         6000
      251        21436            16788         7530
      301            -            14384         8970
   控制端在 20–30 MB 之间来回（解码器/帧缓冲的抖动，不是单调增长）；
   被控端 3 分钟里稳定在 16788 kB，会话结束后回落到 14384 kB。
   **两段加起来 20 分钟里没有单调增长的趋势**，但这不是泄漏证明，只是「没有明显泄漏」。

3) 半开连接（`systemctl --user kill -s STOP uulan-host`）用新目录看，判定链是通的：
   - t=0（刚 STOP）：`在线 1 / 空闲 2s`
   - t≈52 s：`在线 0 / 麒麟真机 离线`（TTL 45 s + sweep 10 s）
   - t≈72 s：仍离线
   - `kill -s CONT` 后 4 秒：`在线 1 / 空闲 3s`，且被控端 `MainPID=2334638`、
     `NRestarts=21` **都没变**（进程从没死），journal 里是
     「与中继的连接断了，稍后重连（进程不退出，设备 ID 不变）」→「已用原有设备 ID 上线」。

六、边界与未验

- 目录只覆盖「这台中继知道的设备」：换一台中继、或台账文件丢了，清单就没了
  （设备下次上线会重新登记）。它不是资产管理系统。
- **没有鉴权**：默认任何能连到中继端口的人都能拉清单（与 `Query` 同一信任模型）。
  敏感现场用 `--no-list` 关掉；现在没有「凭口令看清单」这种中间档，刻意不做 ——
  中继是盲转发，不持有任何凭据。
- `idle_s` 的分辨率是秒；心跳 10 秒一次，所以它反映的是「心跳年龄」，不是「有人在操作」。
- 未验：几十台设备同时在线时的目录规模（字段都很小，8 MiB 帧上限远够；
  但没实测过 100+ 条在真机上的一次查询耗时）。

七、下一步（候选）

- M5 剩余两项仍然只能等人到机器跟前：整机重启后的开机自启、root 系统装路径（`/opt/uulan`）。
- 长连接稳定性：本轮做了 15+5 分钟、20 分钟总计的 soak（见第五节），没有明显泄漏；
  但要「证伪泄漏」得跑小时级、并且跨多次重连（每次重连会换解码器）。下一轮候选。
- `--devices` 之后自然的一步是「控制端记住上次连的设备」（本机配置里存最近一次
  server/device/name），省掉每次敲 9 位数字；同样属于现场可用性，不是协议改动。

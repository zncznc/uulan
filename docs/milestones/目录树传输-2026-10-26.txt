uulan · 目录树传输（--put-tree / --get-tree）· 2026-10-26 夜间批（第一轮）

────────────────────────────────────────────────────────────────
一、为什么做这一项

M4 的文件传输原本只有单文件：--put / --get 一次搬一个文件。现场（乃至我们自己）要往被控端
送一整个工具包 / 部署目录时，只能自己写外面那层循环 —— 于是三件事全落到用户身上：
谁去建远端那些子目录、空目录怎么过去、某个文件失败要不要停。

这一项**没有新增任何树传输协议消息**：树传输就是一串串行的 Mkdir / Put / Get / List。
被控端不知道也不关心对面在搬一棵树，所以不用升协议版本、不用两端同批升级。
唯一动到协议的是给 `FsEntry` 加了一个可选字段 `link`（见第三节），它带 `serde(default)`，
老对端不发就是 false，行为同改动前。

────────────────────────────────────────────────────────────────
二、做法（crates/uulan-client/src/tree.rs）

1) 先规划、再动手
   上传前把本地树走一遍，打印「目录 / 文件 / 字节 / 跳过符号链接」总量，然后才开始建目录发数据。
   用户看到的第一行就是总量，中途断了能立刻算出缺多少。

2) 上传 DFS、下载 BFS
   - 上传：目录先建、文件后传（深度优先）。执行顺序就是计划顺序。
   - 下载：先建完一层目录再搬文件（广度优先）—— 出错时本地是一棵「形状完整、内容缺」的树，
     比一条深深的半截路径好排查。
   目录排序后再走：同一棵树在哪台机器上都产出同一份计划，两次传输的日志才能对比。

3) 一个文件不完整就不算传完
   每个文件仍然走 `.uulan-part` + sha256（与单文件传输同一套语义），
   所以「目标文件存在」永远等于「内容完整」。

4) 幂等建目录的判据是「再列一次」
   被控端的 Mkdir 在目录已存在时回 `已存在：<path>`。不去匹配这句中文错误串（换个措辞就失效），
   而是 Mkdir 失败后再 List 一次：能列出来就是目录，列不出来才是真失败。
   于是「重复 --put-tree 到同一目标」是安全的（本机与真机都实测：第二次照旧成功、字节数一致）。

5) 请求 id 每条一个、不复用
   被控端 `mux.register(id)` 在 id 还被上一条流占着时返回 None。串行复用同一个 id 虽然能过，
   但中间有一个心跳窗口；编号一直加最省心（从 2 起）。

────────────────────────────────────────────────────────────────
三、安全边界（这一节比功能本身重要）

- **本地符号链接一律跳过并计数**。跟随会把一棵树变成图：指回上级就无限递归，
  指到 /etc 就把被控端的系统文件搬过来。
- **远端条目名要过 safe_name**（挡空名、`.`、`..`、含 `/`、`\`、NUL）。被控端回的名字是
  对面的数据，直接拼本地路径等于把「往哪写」交给对面 —— 这一条有单测。
- **下载侧原来会对着链接发呆**：`read_dir` 的 `file_type()` 不跟随链接，所以「指向目录的链接」
  在 `dir` 字段上其实是 false，看起来像个普通文件 —— 原来的 `--get-tree` 会对它发起 Get，
  得到一句「不是目录」，整棵树就断在这儿；指向文件的链接则会把目标内容悄悄复制成本地副本
  （真机上就是 `evil.txt -> /etc/passwd`）。修法：`FsEntry` 加 `link: bool`
  （`#[serde(default)]`），被控端用不跟随的 `file_type()` 标出 `is_symlink()`，
  下载侧见到就跳过并单独计数；控制端 `--ls` 也用 `l` 标出来。

五、真机实测（麒麟 V10 SP1 / 海光 C86 / X11 1920x1080）

部署：从 HEAD 打包 → 真机换源码（保留 target/ 缓存）→

（systemd 自己发信号，无人值守下绕开审批）。前缀与 target/release 三个二进制 sha256 逐个一致；
host 用原有设备 ID 805747189 上线，两个服务 active。

① 画面基线（防回归）：12 秒 headless，355 帧 / **29.6 fps** / **丢帧 0** / 首帧 **224 ms** /
   9788 kbps / 被控端自报 30.00 fps；与真机 `ffmpeg -f x11grab` 截图逐像素比对
   **相关系数 0.9978、MAE 1.82/255 = 0.72%**（基线 0.9982 / 0.71%）。
② Windows 客户端 `--put-tree` → 麒麟 `~/uulan-tree-final`：
   目录 6 / 文件 6 / **4194327 字节**（含一个 4 MiB 文件）/ 0.1s；
   真机 `find + sha256sum` 与本地清单 **6/6 完全一致**；空目录 emptydir、中文目录 文档 都在。
③ 同一个远端目录 `--get-tree` 拉回 Windows：6/6 逐文件 sha256 一致，空目录、中文目录都在。
④ 再传一遍（幂等）：退出码 0，仍是 6 目录 / 6 文件 / 4194327 字节，远端文件数 6。
⑤ 真链接 · 上传侧（用麒麟自己编的客户端，源树由 Linux 建，是真符号链接）：
   源树 = a.txt + sub/b.txt + `evil.txt -> /etc/passwd` + `sub/up -> ..`
   结果：目录 1 / 文件 2 / 11 字节 / **跳过符号链接 2**，退出码 0；
   远端只有 a.txt 与 sub/b.txt，**evil.txt 没有被带过去**，也没有无限递归。
⑥ 真链接 · 下载侧：先在远端树里塞 `evil2.txt -> /etc/passwd` 与 `sub/up2 -> ..`，
   再 `--get-tree` 回来：日志两行「跳过符号链接：evil2.txt / up2」，
   摘要「目录 1 / 文件 2 / 共 11 字节 / **跳过符号链接 2**」；本地没有 evil2.txt，a.txt sha256 一致。

六、边界与未验

- 不支持断点续传 / 增量同步：每次都整棵传，重传靠 sha256 保证正确但不省流量。
  （被控端 Put 是「先写 .part 再改名」，所以正在用的文件不会被传成半截。）
- 不支持删除远端多余文件（不做 --delete）：远控里「删错一棵树」不可挽回，
  删除仍然只能一个一个目录来（--rm 对非空目录会拒绝）。
- 传输是**串行**的：一次一个文件。千兆内网里 4 MiB 用了 0.1s，瓶颈不在这儿；
  要更快得在 bulk 上并行多条流，那是另一项。
- 文件名里不能有 `\`（`safe_name` 会挡掉并计数）：远程路径里两种分隔符混用会变成猜谜。
- 本机（Windows git-bash）造不出真符号链接，所以「跳过链接」的两条断言分别在
  真麒麟（⑤ 上传侧）与被控端 Linux 单测（下载侧的 `link` 标记）里验；Windows 上覆盖不到。

────────────────────────────────────────────────────────────────
七、顺带修掉的一个「只在 Linux 上红」的测试

在真麒麟上第一次跑 `cargo test -p uulan-fs --lib` 时，`get_of_a_directory_is_rejected`
报 `读 bulk 帧: early eof`。功能是对的，错在**测试助手**：`get_file()` 无条件
「一直读 bulk 直到 End」，而失败的 Get（目标是目录）**一个帧都不发**，服务端收工就关掉
duplex → 助手读到 EOF 就把「正确的失败」判成环境错误。
Windows 上这条用例一直在「跳过」，所以从没暴露。修法是助手加 `recv_opt()`（读不到就返回 None），
功能代码一行没动。改后真麒麟 34/34 全绿。

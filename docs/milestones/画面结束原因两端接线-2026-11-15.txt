画面中断的原因由被控端自己说（H2C::VideoError 两端接线）
归档时间：2026-11-15 05:00–06:00 夜批（HEAD af5ef0f 起）
状态：本机已验（含真链路）· **真机未验**（麒麟 192.168.223.15 整轮不在二层，见文末审计）

────────────────────────────────────────────────────────────────
一、这轮修的是什么
────────────────────────────────────────────────────────────────
上一轮（2026-10-26）给控制端加了 15 秒静默看门狗，治好了「TCP 半开时画面定格、
程序看着正常、永不重连」。但它留下一个更隐蔽的错判：

  被控端的编码源在会话中途死掉时，`video_loop` 是**直接 return** 的
  （两条路径：`next_au()` 返回 EOF 且尺寸没变 / 读编码输报错且尺寸没变）。
  视频通道就这么安静地关了，控制端那边唯一的观测是「帧不来了」，
  于是 15 秒后被看门狗判成「连接半开？」。

结论是猜的，而且猜错的方向最害人：现场照着「半开」去查网络（中继、交换机、网线），
而真正死的是对面的 ffmpeg / X 服务器。`H2C::VideoError` 在协议里躺了很久，
注释写着「控制端据此提示用户，而不是黑屏干等」—— 两端谁都没接。
本仓库的老毛病「协议先行、两端未接」再一次现形（同上一轮的音频状态）。

────────────────────────────────────────────────────────────────
二、改了什么
────────────────────────────────────────────────────────────────
被控端 `crates/uulan-host/src/session.rs`
  · `VideoEndCause`（Eof / ReadErr）+ 纯函数 `video_end_message(cause, frames,
    keyframes, bytes, unbounded) -> (String, bool failed)`：三种终止情况各有各的措辞。
  · `report_video_end(..)`：在 `video_loop` 两条**终止**路径 return 之前，把原因
    写进视频通道（`H2C::VideoError`）。分辨率变了那条重启路径**不发**（不是故障）。
  · 「算不算故障」的判据是 **`planned_frames` 与实际出帧对得上**（不是「有界/无界」）：
    有界合成源（`lavfi:…@N`）放满 N 帧 = 按计划收工；没设上限的源（含生产用的 x11grab）
    stdout 到尽头 = 意外；**设了上限却没放满 = 中途夭亡**（例如 ffmpeg 被人 kill）。
    这一条是自查时收紧的：原来只看 `is_unbounded()`，于是「有界源被中途杀掉」会被
    说成「按计划结束」—— 一次真故障被报成正常收工，比反过来更坏，因为它会把事故抹平。
    把正常结束记成故障同样不行（每轮无人值守验收凭空变红，同音频「Ended 不算 Failed」）。
    两头都有反例测试：`a_bounded_source_killed_halfway_is_not_reported_as_planned`。

协议 `crates/uulan-protocol/src/msg.rs`
  · `VideoError { message, #[serde(default)] failed: bool }`。
    新字段可省略 ⇒ **两端不必同批升级**（老被控端发的 JSON 新控制端照解，
    老控制端见到新消息仍落到它原有的 `Ok(_) => {}`）。

控制端 `crates/uulan-client/`
  · `watch.rs`：`PumpEnd::Ended{message, failed}`；`WatchStats::note_video_end`
    （存最后一句，空消息不许抹掉已有原因）+ `video_failed`。
  · 顺带修掉两处「原因被吞」：会话中途的二进制 `Bye` 帧与 JSON `Bye` 原来只写
    `debug!` 日志就当成 `Closed`，现场永远看不见对面说了什么。现在都带进原因。
  · 等第一条 `VideoCfg` 期间收到 `video_error` → 新增 `WatchError::EncoderGone`，
    映射到 `OpenError::Transient`（**不是** Refused）：重连会让被控端重新起一次
    编码器，那正是对症的补救，与「对面拒绝推流」处置方向相反。
  · `session.rs`：收尾原因的优先级改成 **① 被控端自己说的 → ② 本机静默推断 →
    ③ 承认不知道**（以前只有 ②③，被控端编码器死掉时印的是「画面流结束」）。
    `Totals.video_failures` 跨会话只数故障。
  · `main.rs`：headless 收工统计新增一行可 grep 的
    `画面结束   : …（被控端报编码器故障 N 条会话）`；`--json` 加
    `video_end` / `video_failed` / `video_failures`。窗口标题沿用 `drive` 那句原因，
    不需要另改。

工具 `scripts/lan-presence-audit.py`（本轮补提交）
  · 技能文档一直把它当「失联定位的可复用扫描器」引用，但它**从没进过仓库**
    （`git log --all -- scripts/lan-presence-audit.py` 为空）。本轮正撞在真机失联上，
    就把它补成正式工具：控制探针自证扫描可信 → netsh 邻居表拿二层真相 →
    全段特征端口慢扫 + banner 判机型 → 明确「ARP 缺席只能排除还在本子网」。
    退出码 0=在线 / 1=不在本子网 / 2=扫描不可信（代理劫持）。

  · 新增真二进制跨进程验收脚本 **`scripts/verify-video-end-e2e.sh`**（与 `cargo test`
    互补：跑的是发布出去的三个 exe，进程间真网络 + headless 统计行）。两个用例把口径
    两头都钉住：A 有界源放满 → failed=false、「按计划结束」、故障 0 条会话；
    B 不设上限的源自然到头 → failed=true、「意外结束」、故障 1 条会话。
    另外每个用例都断言「没有出现『半开』」「统计行不是『被控端未说明』」「三份日志
    搜不到口令」。二进制一律先拷到工作区之外（`UULAN_STAGE`，默认 D:/uulan-bin/video-end）。

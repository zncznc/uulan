三、M3 键鼠注入：真机实测（Xvfb :99 + xev/xdotool 当独立判据）

四、M4 终端（Linux 侧）：真机实测
--------------------------------

    printf 'tty; echo "SHELL=$0"; stty -a | head -3; echo UULAN-TERM-$((6*7)); exit 7\n' \
      | uulan-client ... --term --term-shell /bin/bash

    tty            → /dev/pts/1                       ← 真 PTY（/dev/ptmx 路径）
    $0            → /bin/bash；提示符 mis@mis-pc:~$    ← 麒麟 bash 启动文件生效
    stty          → speed 38400 baud; rows 30; columns 120; line = 0
                    intr=^C / erase=^? / kill=^U ……    ← termios 默认值齐、winsize 已按 --term-size 下发
    输出          → UULAN-TERM-42
    客户端退出码  → 7                                  ← 远端 shell 的退出码原样回来

收尾（SIGHUP → SIGKILL 升级）：

    交互式 bash 里 `bash -c 'trap "" HUP; sleep 300' &` 之后关会话：
      host 日志：终端会话结束 id=1 code=129
                 WARN 终端会话不响应 SIGHUP，补 SIGKILL      ← 升级路径真的走到了
      结果：**忽略 SIGHUP 的那个进程活下来了**（pid 522630 / sleep 522631）
    对照：普通后台作业 `sleep 300 &` 关会话后**被清掉**（bash 退出时 HUP 自己的作业）
      → 残留 0

    口径：普通作业会被收干净；显式 `trap '' HUP` 的进程会活下来 —— 这正是 nohup 语义，
    不是缺陷，但**必须写进文档**（用户拿它当 nohup 用，别指望关会话就杀掉）。
    已清理本轮留下的 522630/522631。

五、X11 剪贴板：发现并修掉一个只在真机暴露的 ABI bug
--------------------------------------------------

现象（修前，真机 :0，对面是一个自己写的独立 Xlib 客户端 `/tmp/xclip-or`）：

    我们的探针读对面 → "读剪贴板超时（所有者未响应）"，GET-BEFORE none
    对面读我们的     → 对方永远等不到 SelectionNotify（卡住）
    自己读自己       → 永远成功（走 own_text 缓存，根本不经过 X 协议）

根因：`crates/uulan-clip/src/x11.rs` 用**一个**结构体同时表示
`XSelectionRequestEvent`（有 owner 字段）和 `XSelectionEvent`（SelectionNotify，**没有** owner）。
于是处理 notify 时所有字段整体错位一格：

    se.requestor  ✓（都在 offset 32）
    se.selection  读到的是 target
    se.target     读到的是 property
    se.property   读到的是 time     ← 于是"所有者拒绝"判断和"是不是 CLIPBOARD"判断全错
    我们回给别人的 notify 里 selection 填的是窗口号 → 对方一律忽略

修法：拆成三个结构体（request / notify / clear），各自按 Xlib ABI 声明；
并加了布局断言（`selection_event_layouts_match_xlib`：64 位下 80/72/56 字节、
关键字段 offset，以及与指针宽度无关的三条结构关系）——下次再有人"合并结构体"会立刻红。

修后真机实测（同一个独立客户端当判据）：

    GET-BEFORE len=17 <<<ORACLE-OWNED-7f3a>>>     ← 我们的 requestor 侧读到外部 owner 的内容
    SET-OK <<<PROBE-WRITE-42>>>
    外部客户端：OR-GET len=14 <<<PROBE-WRITE-42>>> ← 我们的 owner 侧能应答外部 requestor
    客户端退出后：X11 剪贴板内容随所有者失效（X11 固有行为，文档已写明）

整链（Windows ↔ 麒麟 :0，窗口模式 22 秒）本轮**只验到一半**：

    被控端统计：sent=1（读到麒麟侧剪贴板并发出）、recv=0
    控制端统计：clips_recv 失败 1 次 → "写本机剪贴板失败"

    原因不在代码：本轮是 cron 上下文，Windows 这一侧**没有可用的交互式剪贴板** ——
    同一个进程里 `Set-Clipboard 'ABC'` 之后 `Get-Clipboard` 读回空串（len=0），
    PowerShell 的跨进程读写也是空。所以"Windows 剪贴板"这条路本轮无法驱动/观测。
    ⇒ 未验：Windows↔麒麟 剪贴板整链（需要用户在桌面会话里跑
      `bash scripts/verify-clipboard-e2e.sh`，或用窗口模式手动复制一次）。

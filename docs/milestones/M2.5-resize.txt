uulan 里程碑 M2.5（分辨率变化重建解码器）—— 两端都做了，真机待验 ✅（本机全链路实测）

【本轮做了什么】
  控制端 crates/uulan-client/src/watch.rs：
    整条解码流水线改成「按代」重建 —— 新增 supervise（总管任务）+ pump_generation（收一代的帧）
    socket 用 into_split()，两个半端靠 pump 任务的返回值在换代之间交接（TCP 不断）
    VideoCfg 画幅变了 → abort feed/decoded、kill 旧解码器、起新解码器、接着收
    只报帧率的 VideoCfg 不触发重建（每 2 秒一次的那种）
    通道正常关闭时先等 ffmpeg 冲刷完（2 秒超时）再 kill
    WatchStats 新增 resizes / cfg_w / cfg_h，并提供 size()
  被控端 crates/uulan-host/src/session.rs：
    ScreenProbe（可注入的尺寸探针）+ probe_once（spawn_blocking + 3 秒超时）
    production_probe：抓 X11 且配置没钉死尺寸时用 xdpyinfo；钉死/合成源一律 None
    video_loop：1 秒一次探针；尺寸变了就停源、按新尺寸重开、发新 VideoCfg
                编码源报错时也先探一次（分辨率变小时 x11grab 往往先崩）
    InputLoop：新增 size_rx + sync_screen()，在换算坐标之前把新尺寸同步给 Mapper
    （否则画面换尺寸、点击落点还按旧尺寸算）
  capture.rs：
    to_ffmpeg_input 里的 lavfi spec 跟随画幅（with_size 改写 size=WxH，别名不动）
    detect_x11_screen_blocking（给同步探针用）
  main.rs：统计里多打「当前画幅 WxH」「解码器重建 N 次」，JSON 加 resizes

【控制端单独一代 crates/uulan-client/tests/resize_path.rs】
  假发流器按协议写：VideoCfg 320x240 → 一段 320x240 码流 →
                    一条只报帧率的 VideoCfg(320x240, fps=14.7) → VideoCfg 480x360 → 一段 480x360 码流
  实测：帧：320x240 3 帧 / 480x360 1 帧；重建 1 次；解出 4 帧 / 喂入 2 AU / 丢帧 0
  断言：三条 VideoCfg 只重建一次（帧率上报不触发）；两代帧字节数各自正确；
        除 320x240 / 480x360 外不出现第三种画幅；stats.cfg_w/h 跟到最新值

【两端全链路 crates/uulan-client/tests/resize_host.rs】
  真 server + 真被控端会话 + 真 lavfi 采集 + 真 x264 + 真协议 + 真 ffmpeg 解码；
  替身只有两处：尺寸探针（本机没有 X11）、注入 sink（记录型）。
  流程：先解 3 帧 320x240 → 把探针的原子量改成 480x360 → 再解 3 帧
  实测：帧：320x240 3 帧 / 480x360 3 帧；重建 1 次；解出 349 / 喂入 456 AU / 丢帧 4386
  断言：换之前只出 320x240；换之后出足够的新尺寸帧；stats.resizes >= 1；
        换之后 (0.5,0.5) 注入成 MoveAbs{240,180}（不是 160,120）—— 坐标按新尺寸换算
  （丢帧 4386 = lavfi 不限速跑满 CPU，真机 x11grab 30fps 不会这样）
